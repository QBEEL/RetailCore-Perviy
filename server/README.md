# Серверная часть RetailCore

Общая база оплат: раньше `payments.db` лежал в профиле одного человека, и
остальные категорийные менеджеры оплат не видели. Здесь то же самое, но на
сервере и с учётными записями.

## Что где

| Путь | Что это |
|---|---|
| `docker-compose.yml` | Три контейнера: база, API, Caddy |
| `db/schema.sql` | Схема. Применяется автоматически при первом запуске на пустом томе |
| `api/` | FastAPI: вход по логину, токены, права, оплаты, бюджеты, вложения |
| `Caddyfile` | HTTPS для `retail.qbeely.ru`, сертификат продлевается сам |
| `tools/export_from_sqlite.py` | Выгрузка локальной `payments.db` в файл для загрузки |
| `tools/draft_accounts.py` | Черновик учёток по полю `responsible` из выгрузки 1С |
| `tools/backup.sh` | Ночная копия базы и вложений, в cron на 03:00 |

Адрес: **https://retail.qbeely.ru**, описание методов — `/docs`.

## Права

Читать оплаты может любой, у кого есть учётка. Править — только свои: те, где
`responsible` совпадает с одним из имён, закреплённых за учёткой в таблице
`user_responsible`. Администратор правит всё и заводит учётные записи.

Правило считается на сервере, и в каждой записи ответа приходит готовый признак
`editable` — клиенту не нужно повторять логику и незачем с ней расходиться.

Из выгрузки 1С правятся только «свои» поля: дата, статус, комментарий,
поставщик, сумма, приоритет. Остальное перезапишет следующий импорт.

## Разделы приложения

`user_page_denied` — какие вкладки человеку **не** показывать. Маркировкой
занимаются двое, а вкладка висела у всех восемнадцати; администратор снимает
лишнее в карточке учётной записи, список едет клиенту вместе с токеном.

Хранится закрытое, а не открытое: иначе каждая версия приложения с новой
вкладкой начиналась бы с обхода всех учёток, чтобы выдать право на то, что
вчера работало без спроса, а забытая учётка молча теряла бы раздел.

Это настройка рабочего места, а не право на данные. Доступ к общей базе сервер
считает сам (`editable`, отказ для не-администратора) и от меню не зависит, а
«Маркировка» ходит в «Честный ЗНАК» по личному сертификату и о сервере не знает
вовсе. Коды разделов задаёт приложение и здесь не проверяются — справочник на
сервере пришлось бы догонять миграцией на каждую новую вкладку ради проверки,
которая ничего не защищает.

## Миграции схемы

`db/schema.sql` применяется только к пустому тому. Всё, что меняется потом, —
файлами в `db/migrations`, по порядку имён:

```sh
tools/migrate.sh
```

Применённые запоминаются в `schema_migration`, повторный запуск ничего не
переделывает. Каждая миграция и отметка о ней — в одной транзакции.

## Импорт выгрузки 1С

Выгрузку разбирает приложение — там вся логика распознавания колонок и
статусов. Сервер отдаёт снимок уже записанного (`GET /api/imports/index`) и
принимает разобранное (`POST /api/imports/apply`) одной транзакцией.

Импорт доступен **только администратору**: выгрузка перезаписывает поля во всех
оплатах отдела, включая чужие.

Тонкость, на которой легко ошибиться: снимок должен приходить в том же
представлении, что даёт локальная база (`1`/`0` вместо `true`/`false`, пустая
строка вместо `null`). Сравнение «изменилось ли» идёт через `str()`, и при
несовпадении типов все семь тысяч строк выглядят изменившимися. Приведение
делает `remote._comparable`, проверяется просто: повторный импорт того же файла
обязан дать ноль новых и ноль изменившихся.

## Торг-2: недопоставки и браки

Миграция `013_claims.sql`, методы `/api/claims/*`. Таблицы `claim` и
`claim_file` (файлы лежат в томе рядом с вложениями оплат, в папке `claims/`).

Архив — не отдельная таблица, а заявки со статусом `closed`: возврат из архива
не переносит строки и не теряет вложения.

Права считаются на сервере и приходят в каждой заявке флагами `can_*`.
Заводить и закрывать может любой вошедший; править — заявитель, КМ и
администратор; «принять в работу» — только КМ заявки или администратор;
вернуть из архива — администратор; удалить — администратор или заявитель, пока
заявка новая. КМ — учётка с заданным направлением (`/api/claims/managers`).

Уведомление построено на `claim.manager_seen`: падает в `FALSE`, когда
менеджера назначают или меняют (кроме назначения на себя), и поднимается, когда
он открыл заявку (`POST /{id}/seen`), принял её или закрыл. Приложение раз в
минуту читает `GET /api/claims/inbox` — два счётчика по частичному индексу
`claim_unseen`.

### Бренды и акты ТОРГ-2

Миграции `014_claim_brands.sql` (справочник брендов, начальные 668 из файла склада),
`015_torg_act.sql` (акты и реквизиты для бланка, колонка `claim.act_id`).

`/api/claim-brands` — подсказка при наборе бренда. Добавить может любой (повторное
добавление отдаёт существующий бренд, а не ошибку), убрать — только администратор.
Сравнение без регистра, лишних пробелов и «ё» (`name_key`).

`/api/torg` — акты. Бланк Excel собирает приложение по шаблону
`app/ui/assets/torg2_template.xlsx`, сервер хранит то, из чего он собран: номер, дату,
поставщика и остальное в `payload`. Номер сквозной в пределах года
(`UNIQUE (act_year, number)`), повтор — `409`. Заявка входит не больше чем в один акт;
заявка из чужого акта — `409`. `/api/torg/settings` — общие реквизиты организации и
комиссии (таблица `claim_setting`), правит любой вошедший, каждая правка в журнале.
`/api/torg/next?year=` — следующий номер, `/api/torg/suppliers` — поставщики из прошлых
актов с договором и доставкой.

## Отчётность для поставщиков

Две общие настройки, `/api/reports/*`:

**Профили отчётов** (`report_profile`) — формат отчёта у каждого поставщика свой.
Всё, кроме имени и поставщика, лежит в `payload` нетипизированным `jsonb`: состав
полей, метрик и фильтров задаётся приложением и меняется чаще, чем выкатывается
сервер. Проверять его схему здесь заново — значит выпускать новую версию API на
каждую новую метрику.

**Правила объединения магазинов** (`store_rule`) — «продажи источника учитывать
за приёмником». Одни на весь отдел: если один менеджер учитывает интернет-магазин
за универмагом, а второй нет, сводная по сети перестаёт сходиться, а найти
причину по готовым файлам уже нельзя.

`source_key` нормализован так же, как в приложении (регистр, двойные пробелы,
«ё») и уникален: отправить один магазин сразу в два — это молча удвоенные
продажи. Кольцо (`A → B → A`) проверяется **до записи** и отклоняется с `409`: с
замкнутой цепочкой переносы не применяются вовсе, и менеджер получил бы отчёт по
старым правилам без единого объяснения.

Править может любой пользователь — поправить опечатку должен уметь тот, кто её
заметил. Удалять — только администратор: на профиль и правило опираются чужие
отчёты. Всё пишется в `audit_log`.

## Пароли

- Хранятся как scrypt-хеш, восстановлению не подлежат.
- Выданный администратором пароль владелец обязан сменить при первом входе
  (`must_change_password`), иначе журнал не доказывает, кто правил оплату.
- Пять неудачных попыток на логин за 15 минут — дальше `429`. Удачный вход
  счётчик обнуляет.

## Учётные записи

```sh
# черновик готовится на рабочем компьютере
python server/tools/draft_accounts.py
# вычитывается человеком, затем заводится на сервере
docker compose exec -T api python -m app.seed - < accounts.json
```

Пароль печатается один раз при создании — в базе только scrypt-хеш. Забытый
пароль не восстанавливается, назначается новый:
`POST /api/users/{id}/password`.

На сервере всё это лежит в `/opt/retailcore`, вложения — в `/opt/retailcore/files`,
копии — в `/opt/retailcore/backups` (хранятся 30 дней).

## Развёртывание с нуля

```sh
cp .env.example .env
# пароль сгенерировать, а не придумать:
sed -i "s/замените-меня/$(openssl rand -base64 24 | tr -d '/+=' | head -c 28)/" .env
chmod 600 .env
docker compose up -d
```

### ИИ-правка заметок (необязательно)

Кнопка «ИИ…» в заметках ходит на `POST /api/ai/edit`, а сервер — в Gemini.
В `.env` задаются `GEMINI_API_KEY` (ключ из Google AI Studio; подписка Gemini Pro
для API не подходит), `AI_MODEL`, `AI_DAILY_LIMIT` (обращений на человека в сутки,
по умолчанию 20: квота ключа общая; администратор может задать личный предел в
учётной записи, колонка `app_user.ai_daily_limit`, 0 закрывает ИИ человеку) и, если с сервера Google закрыт, `AI_HTTPS_PROXY`. Без ключа
сервер работает как раньше, а запрос к ИИ получает отказ «не настроен». Перед
первым включением примените миграции `016_ai_usage.sql`, `017_ai_user_limit.sql` и
`018_app_version.sql` (`tools/migrate.sh`) — до пересборки API, иначе список учёток
не прочитается — и
проверьте доступ: `curl -s -o /dev/null -w '%{http_code}\n'
https://generativelanguage.googleapis.com/` с самого сервера. Текст заметок на
сервере не сохраняется, считаются только обращения и объём.

## Перенос данных с рабочего компьютера

```sh
# на компьютере, где ведутся оплаты
python server/tools/export_from_sqlite.py --out payments_dump.sql
# файл заливается на сервер, дальше на сервере:
docker compose exec -T db psql -U retailcore -d retailcore -v ON_ERROR_STOP=1 < payments_dump.sql
```

Выгрузка применяется одной транзакцией: либо переносится всё, либо ничего.
Локальная база при этом не меняется и остаётся резервной копией.

### Как проверять, что перенос удался

Совпадения количества строк недостаточно — на деньгах нужна построчная сверка.
С обеих сторон считается один и тот же хеш, и они должны совпасть побайтово:

```sql
SELECT md5(string_agg(line, E'\n' ORDER BY id) || E'\n') FROM (
  SELECT id, id::text || '|' || doc_number || '|' || COALESCE(pay_date::text,'') || '|' ||
         to_char(amount,'FM9999999999990.00') || '|' || recipient || '|' ||
         status || '|' || responsible AS line
  FROM payment) r;
```

## Восстановление из копии

```sh
gunzip -c backups/retailcore-2026-07-31.sql.gz \
  | docker compose exec -T db psql -U retailcore -d retailcore -v ON_ERROR_STOP=1
tar -xzf backups/files-2026-07-31.tar.gz -C /opt/retailcore
```

Дамп сделан с `--clean --if-exists`, поэтому разворачивается поверх непустой
базы. Проверять восстановление стоит в отдельной базе (`CREATE DATABASE
restore_check`), а не в рабочей.

## Удаление данных

`POST /api/maintenance/wipe`, только администратор. Нужно, когда выгрузку из 1С
переносят заново и накопленное с ней уже не сходится: дописывать такую выгрузку
к старой бессмысленно, сойдётся она только с пустой базой.

Стирается `payment`, `payment_file` (вместе с файлами в `files_dir`), `budget`,
`import_run` и `recipient_link`. Остаются учётные записи, направления,
закрепление поставщиков и `audit_log` — восстанавливать их руками дольше, чем
повторить импорт, а запись о самом удалении попадает в тот же журнал
(`entity = database`, `action = wipe`, в `changes` — сколько чего стёрлось).
Сколько сотрётся, заранее показывает `GET /api/maintenance/scope`.

Подтверждений два: слово `УДАЛИТЬ` в теле запроса и пароль администратора.
Токена мало — он живёт двенадцать часов в памяти открытого приложения, и
незапертый компьютер не должен означать пустую базу.

`DELETE`, а не `TRUNCATE`: счётчики идентификаторов продолжаются с прежнего
места. Скачанные вложения кэшируются у менеджеров по номеру оплаты, и после
сброса счётчика новая оплата открывала бы чужой файл из кэша.

Всё удаление идёт одной транзакцией, но восстановить его нечем — только из
ночной копии, как выше. Перед удалением стоит убедиться, что копия свежая.

## Чего здесь намеренно нет

**Порт базы наружу.** PostgreSQL слушает только `127.0.0.1`. Приложение будет
ходить через HTTP API, а для ручного доступа хватает SSH-туннеля:

```sh
ssh -L 5433:127.0.0.1:5433 root@191.44.112.174
```

### Версия приложения у пользователей

Приложение присылает версию и систему в заголовках `X-App-Version` и
`X-App-Platform` каждого запроса. Сервер запоминает их у учётки вместе со временем
последнего обращения (`app_user.app_version`, `app_platform`, `app_seen_at`; миграция
`018_app_version.sql`): при смене версии сразу, иначе не чаще раза в час. Видно это в
«Администрирование → Учётные записи». Версия не проверяется на соответствие и не
влияет на доступ: значение вне вида `3.9.2` отбрасывается, сбой записи запрос не
останавливает. У приложений старше 3.9.2 поле пустое.
