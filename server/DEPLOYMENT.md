# Запуск, миграции и обновление сервера

Команды выполняются из каталога `server` (в рабочем окружении —
`/opt/retailcore`). Нужен Docker Compose v2 с поддержкой `--wait`.

## Запуск с нуля

Подготовьте `.env` по `.env.example`: пароль PostgreSQL и `API_SECRET` должны
быть сгенерированы отдельно. Для ключа подписи подойдёт `openssl rand -hex 32`.
API требует ключ не короче 32 символов, а compose блокирует запуск с пустым
ключом. Не заменяйте ключ подписи при обычном обновлении: это завершит
действующие сессии.

```sh
(
set -eu
mkdir -p files
chown 1001:1001 files
docker compose up -d --build --wait --wait-timeout 180
docker compose exec -T api python -m app.migrations --check
)
```

Compose ждёт PostgreSQL, затем запускает одноразовый сервис `migrate`.
Мигратор создаёт базовую схему в пустой базе и применяет все SQL-миграции.
При его ошибке API не запускается. Затем API самостоятельно проверяет историю
схемы, проходит HTTP healthcheck, и только после этого запускается Caddy.
Код API и SQL входят в один образ. `.env`, вложения и бэкапы исключены из
контекста сборки через `.dockerignore`.

## Обновление существующего сервера

Сначала проверьте новую версию на отдельной базе. На рабочем сервере
обновление выполняется с короткой остановкой API, чтобы резервная копия базы
и вложений не расходилась с изменениями пользователей. После доставки новой
версии файлов, с сохранением рабочего `.env`:

```sh
(
set -eu
# Сохранить работающий образ и собрать новый до остановки пользователей.
docker image tag "$(docker inspect --format '{{.Image}}' retailcore-api)" retailcore-api:before-update
docker compose build api migrate
docker compose stop api
sh tools/backup.sh
sh tools/migrate.sh
docker compose up -d --no-deps --wait --wait-timeout 120 api
docker compose up -d --no-deps caddy
docker compose exec -T api python -m app.migrations --check
)
```

Команды выполняйте последовательно: при ошибке не переходите к следующей.
Бэкап должен завершиться до миграций. Если ошибка в SQL, API остаётся
остановленным; исправьте ещё не применённый файл и повторите мигратор.
Причину отказа показывают `docker compose logs migrate api`. При ручном запуске
через `sh tools/migrate.sh` вывод мигратора виден прямо в терминале.

## Как устроены миграции

`api/app/migrations.py` выполняется как `python -m app.migrations`. Команда
`sh tools/migrate.sh` запускает его в контейнере; с `--check` он только проверяет
готовность схемы. Адрес и учётные данные берутся из `DATABASE_URL`.

Сессионная блокировка PostgreSQL не даёт двум миграторам выполнять SQL
одновременно. Ожидание блокировки ограничено 60 секундами. Каждый файл и его
запись в `schema_migration` выполняются в одной транзакции: ошибка откатывает
текущий файл, а предыдущие успешные остаются применёнными.

Журнал хранит имя, время и SHA-256 каждого применённого файла. Повторный запуск
не выполняет SQL заново и не меняет время. Правка применённого файла или пропуск
в истории блокирует миграции. Базовую `db/schema.sql` тоже не меняют: новое
изменение добавляют следующим номером в `db/migrations`. Перевод CRLF/LF не
меняет хеш. Мигратор не откатывает базу к более старому набору файлов.

Старый shell-скрипт сохранял только имя и время. Новый мигратор добавляет хеши
без повторного исполнения SQL и сохраняет прежнее время. Историческую версию
этих файлов старый журнал подтвердить не может: при первом переходе хеш
вычисляется по файлам текущей поставки. Если SQL применяли вручную без записи
в журнал, сначала восстановите достоверную историю: автоматически угадать,
какие изменения данных уже выполнены, нельзя.

API проверяет наличие и хеши своих миграций при старте; при отказе пул
соединений закрывается. Более новые записи в базе допускаются этой проверкой.
Она не проверяет все таблицы на произвольные ручные изменения и не доказывает
совместимость старого кода с новой схемой.

## Возврат предыдущей версии

Если схема совместима со старым кодом, сохранённый образ можно вернуть:

```sh
(
set -eu
docker image tag retailcore-api:before-update retailcore-api:latest
docker compose up -d --no-deps --wait --wait-timeout 120 api
)
```

Это возврат кода без автоматического отката SQL. При несовместимом изменении
нужно восстановление базы и вложений из одной копии. Сначала проверьте его
в отдельной базе по инструкции в README. Не удаляйте Docker volume для
исправления ошибки миграции.

## Резервная копия

`sh tools/backup.sh` сначала записывает дамп, затем отдельно сжимает его и
архивирует вложения. Сбой `pg_dump` больше не скрывается успешным завершением
`gzip`. До успешного выполнения этих шагов файлы имеют суффикс `.part`.
Имена новых копий содержат время до секунд, поэтому повторный запуск в другой
момент дня не перезаписывает ночную копию. Для временного несжатого дампа нужно
дополнительное место на диске.

Перед обновлением API должен быть остановлен. Обычная ночная копия работающего
приложения не обеспечивает единого снимка базы и файлов при одновременной
загрузке или удалении вложений. В cron скрипт запускается через `sh`:

```cron
0 3 * * * sh /opt/retailcore/tools/backup.sh >> /var/log/retailcore-backup.log 2>&1
```

## Проверка

В CI отдельная задача PostgreSQL 16 проверяет создание с нуля, обновление,
повторный и параллельный запуск, откат ошибочного файла, переход со старого
журнала, защиту от изменения применённого SQL и старт API. Там же собирается
и запускается свежий compose-стек без Caddy. Ошибки бэкапа проверяются с
отказами `pg_dump`, `gzip` и `tar`.

Локально из корня проекта, после установки `requirements-test.txt`:

```sh
export RETAILCORE_TEST_DSN='postgresql://test_user:test_password@127.0.0.1:5432/postgres'
python -m pytest tests/test_server_migrations.py tests/test_server_backup.py -q -ra
```

Используйте отдельный тестовый PostgreSQL: роль должна иметь право создавать
базы. Каждый тест создаёт базу `retailcore_test_<случайное имя>` и удаляет только
её. Без `RETAILCORE_TEST_DSN` проверки PostgreSQL пропускаются; в CI переменная
задана обязательно.
