# Вкладка «Поставщики» — переработка

Техническое задание. Код не написан. Ниже: что сломано сейчас, какая модель
приходит взамен, порядок работ. Спорные места согласованы — принятые решения
и их основания собраны в конце.

---

## 1. Что сломано

### Менеджер не назначен, а вычислен

`app/core/payments/store.py:548` и `server/api/app/routers/payments.py:161`
считают менеджеров поставщика группировкой `payment.responsible` и сортируют по
количеству оплат. То есть «менеджер поставщика» сегодня означает «кто ему чаще
платил». Это статистика, а не закрепление, и отсюда все жалобы:

- разовая оплата за коллегу навсегда добавляет человека в список менеджеров;
- поставщик, которого менеджер ведёт, но по которому ещё не было оплат, у него
  не показывается вовсе;
- в подписи строки стоит тот, у кого оплат больше, а не тот, кто ведёт.

Последнее уже пришлось лечить костылём: поле `focus` в `app/ui/suppliers_page.py:63-84`
подставляет в подпись того менеджера, по которому шёл отбор, — иначе при фильтре
«мои» у поставщика значится чужое имя. После переработки поле удаляется.

### `responsible` не нормализован

Это свободный текст из выгрузки 1С. По комментарию в `server/db/schema.sql:34` —
57 различных написаний примерно на полтора десятка живых людей. Таблица
`user_responsible` сводит написания к учётной записи, но используется только для
прав на правку. Группировка в списке поставщиков идёт по сырой строке, поэтому
один человек попадает в фильтр несколько раз.

### Направлений нет как сущности

Beauty и Fashion не встречаются в моделях ни разу. Это не сломанный фильтр —
это отсутствующее поле, его нужно заводить с нуля вместе со справочником.

### Сортировка недоступна пользователю

Порядок зашит в SQL — `ORDER BY SUM(amount) DESC`. Список рисуется `QListWidget`
двухстрочным текстом (`app/ui/suppliers_page.py:487`), а не таблицей, поэтому
сортировать по колонке физически нечем.

## 2. Модель

### Три разных понятия вместо одного

| Понятие | Что это | Откуда берётся |
|---|---|---|
| **Направление** | Beauty / Fashion | Свойство поставщика. Задаётся явно |
| **Закреплённый менеджер** | Кто ведёт поставщика | Назначается руками, фиксирует админ |
| **Кто платил** | Факт из выгрузки 1С | Считается по оплатам, только для справки |

Сегодня все три слиты в одно вычисляемое поле. Разделение — суть переработки.

### Менеджер ↔ поставщик: многие-ко-многим

Один менеджер ведёт несколько поставщиков, и **у одного поставщика может быть
несколько менеджеров** — «Суперкосметикс ООО» ведут Евгений Иванов и Карина
Валева, каждый по своим брендам. Единственного владельца назначать нельзя: это
исказит реальность у части поставщиков.

Поэтому закрепление — таблица связей, а не колонка. «Мои поставщики» = те, где
я есть в списке закреплённых.

Разделение по брендам внутри поставщика не хранится: в карточке «Суперкосметикс»
стоят две фамилии без расшифровки, кто за какие бренды отвечает. Так решено
сознательно — поле пришлось бы заполнять руками при каждом закреплении, а
пользы в отборе и фильтрах оно не даёт.

### Направление ↔ поставщик: тоже многие-ко-многим

Поставщик в обоих направлениях — случай редкий, но реальный, поэтому связь
множественная. В интерфейсе оптимизируем под один случай: первое направление
показывается бейджем, второе — плюсом рядом.

**Правило по умолчанию:** при фиксации закрепления направления поставщика
проставляются как объединение направлений закреплённых за ним менеджеров.
Ведут Иванов и Валева, оба Beauty — поставщик Beauty. Ведут Баранова (Fashion) и
Иванов (Beauty) — поставщик в обоих. Админ может переопределить вручную; тогда
запись помечается `source='manual'` и автоправило её больше не трогает.

Направление менеджера хранится отдельно (`user_direction`) и тоже допускает
несколько значений — на случай, если кто-то ведёт оба отдела.

### Порядок закрепления

Двухшаговый, как вы и просили:

```
менеджер выделяет своих     админ проверяет очередь        закрепление
поставщиков в таблице   →   и нажимает «Зафиксировать»  →  действует
     (draft)                        (fixed)                 правит только админ
```

- **draft** — менеджер заявил. Может отозвать сам, пока не зафиксировано.
- **fixed** — админ подтвердил. Менеджер больше не правит; снять или переназначить
  может только админ.

Заявленный поставщик считается «моим» **сразу**, не дожидаясь фиксации: в фильтре
«Мои» он появляется в тот же момент с пометкой «на подтверждении». Иначе между
заявкой и фиксацией менеджер не видит собственный список и работать ему нечем.
Фиксация меняет не видимость, а право на правку.

Все переходы пишутся в журнал (кто, когда, что) — база общая, и без журнала
разбирательство «кто отобрал у меня поставщика» упирается в слово против слова.

### Оплата не своему поставщику

Не блокируется. Если `responsible` оплаты не входит в число закреплённых
менеджеров получателя — предупреждение в двух местах:

- бейдж в строке таблицы оплат;
- в карточке поставщика строка «платили, но не закреплены: …».

## 3. Хранение

**Важно для планирования сроков:** закрепления и направления опираются на
`recipient_key` — ключ получателя из базы оплат, которая **уже общая**. Поэтому
вся эта часть выкатывается без переноса карточек поставщиков. Перенос локального
`suppliers.db` на сервер — отдельный, независимый этап, и он не блокирует главное.

### Новые таблицы на сервере

Миграция `server/db/migrations/00X_supplier_directory.sql`:

```sql
-- Справочник направлений. Таблица, а не enum: список будет пополняться.
CREATE TABLE direction (
    id         SMALLSERIAL PRIMARY KEY,
    code       TEXT    NOT NULL UNIQUE,          -- beauty, fashion
    title      TEXT    NOT NULL,                 -- Beauty, Fashion
    sort_order INTEGER NOT NULL DEFAULT 0,
    is_active  BOOLEAN NOT NULL DEFAULT TRUE
);

-- Направление менеджера. Множественное: кто-то может вести оба отдела.
CREATE TABLE user_direction (
    user_id      BIGINT   NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
    direction_id SMALLINT NOT NULL REFERENCES direction(id) ON DELETE CASCADE,
    PRIMARY KEY (user_id, direction_id)
);

-- Закрепление поставщика за менеджером.
-- Ключ — recipient_key, а не supplier_id: карточка есть у единиц поставщиков,
-- а получатель приходит с каждой выгрузкой 1С.
CREATE TABLE supplier_assignment (
    recipient_key TEXT        NOT NULL,
    user_id       BIGINT      NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
    state         TEXT        NOT NULL DEFAULT 'draft',  -- draft | fixed
    claimed_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    claimed_by    BIGINT      REFERENCES app_user(id) ON DELETE SET NULL,
    fixed_at      TIMESTAMPTZ,
    fixed_by      BIGINT      REFERENCES app_user(id) ON DELETE SET NULL,
    PRIMARY KEY (recipient_key, user_id)
);

CREATE INDEX supplier_assignment_user  ON supplier_assignment(user_id, state);
CREATE INDEX supplier_assignment_state ON supplier_assignment(state);

-- Направление поставщика. source='auto' — проставлено по менеджерам,
-- 'manual' — задано админом вручную, автоправилом не перетирается.
CREATE TABLE supplier_direction (
    recipient_key TEXT        NOT NULL,
    direction_id  SMALLINT    NOT NULL REFERENCES direction(id) ON DELETE CASCADE,
    source        TEXT        NOT NULL DEFAULT 'auto',
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_by    BIGINT      REFERENCES app_user(id) ON DELETE SET NULL,
    PRIMARY KEY (recipient_key, direction_id)
);

CREATE INDEX supplier_direction_dir ON supplier_direction(direction_id);

-- Журнал: кто, когда и что сделал с закреплением.
CREATE TABLE supplier_assignment_log (
    id            BIGSERIAL PRIMARY KEY,
    recipient_key TEXT        NOT NULL,
    user_id       BIGINT,
    action        TEXT        NOT NULL,   -- claim | withdraw | fix | unfix | reassign
    payload       JSONB       NOT NULL DEFAULT '{}',
    actor_id      BIGINT      REFERENCES app_user(id) ON DELETE SET NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### Локальный кэш

`_V3` в `app/core/suppliers/schema.py` — направление и закреплённые менеджеры
рядом с карточкой, только для чтения. Вкладка не должна падать без сервера:
такое поведение уже заложено (`app/ui/suppliers_page.py:116`) и сохраняется.
Заявить или зафиксировать закрепление офлайн нельзя — кнопки гаснут.

## 4. API

| Метод | Путь | Кто | Что делает |
|---|---|---|---|
| `GET` | `/api/directions` | все | справочник направлений |
| `GET` | `/api/suppliers` | все | список с фильтрами и сортировкой |
| `POST` | `/api/suppliers/claims` | менеджер | заявить своими (пачкой) |
| `DELETE` | `/api/suppliers/claims` | менеджер | отозвать заявку до фиксации |
| `GET` | `/api/suppliers/claims?state=draft` | админ | очередь на фиксацию |
| `POST` | `/api/suppliers/assignments/fix` | админ | зафиксировать (пачкой) |
| `DELETE` | `/api/suppliers/assignments` | админ | снять закрепление |
| `PATCH` | `/api/suppliers/{key}/directions` | админ | задать направления вручную |
| `GET` | `/api/suppliers/conflicts` | все | оплаты от незакреплённых менеджеров |

Параметры `GET /api/suppliers`: `direction`, `manager`, `state`
(`fixed` / `draft` / `none`), `search`, `sort`, `order`, `page`, `page_size`.

**Фильтрация и сортировка переезжают на сервер.** Сейчас всё грузится разом и
фильтруется на клиенте — на полутора тысячах поставщиков с новыми фильтрами и
пагинацией это уже неприемлемо.

**Группировка менеджеров — по `user_id` через `user_responsible`**, а не по строке
`responsible`. Написания одного человека схлопываются в одну позицию фильтра.
Строки, не сведённые ни к одной учётке, собираются в псевдоменеджера
«не распознан» — это рабочий список для админа.

## 5. Интерфейс

### Список

`QListWidget` меняется на `DataTable` — тот самый, что уже работает во вкладке
привязок (`app/ui/suppliers_page.py:401`). Колонки:

| Колонка | Сортировка | Примечание |
|---|---|---|
| ☑ | — | множественное выделение для пачки |
| Поставщик | да | |
| Направление | да | бейдж; второе направление — «+1» |
| Менеджеры | да | закреплённые; черновик — курсивом |
| Оплат | да | |
| Сумма | да | по умолчанию сортировка отсюда |
| Последняя оплата | да | |
| Карточка | да | есть структура прайса или нет |

Незакреплённые поставщики не прячутся никогда — они видны с пустым
направлением, это и есть рабочий список на период внедрения.

### Фильтры одной строкой над таблицей

- переключатель направления: `Все | Beauty | Fashion` (из справочника);
- менеджер: `Мои` (первым) / конкретный / `Все` / `Не закреплены`;
- статус: `Все | Зафиксированы | Черновики | Без закрепления`;
- поиск — оставить как есть, он работает.

**Умолчание при открытии:** своё направление + `Мои`. Сейчас выбор умолчания
размазан по `_fill_managers()` (`app/ui/suppliers_page.py:455`) и вызывает
повторный `reload()` — переписать на явную инициализацию фильтров до первого
запроса.

**Чужое направление не прячется.** Отбор по направлению — это умолчание фильтра,
а не право доступа: менеджер Beauty может переключиться на Fashion и увидеть
всё. Ограничивать выдачу на сервере нельзя — сломается главный сценарий поиска
«не помню, чей это поставщик», ради которого вкладкой и пользуются чаще всего.
Права ограничивают правку, а не видимость.

Фильтр `Мои` включает и черновики, и зафиксированное. Черновик показывается с
пометкой «на подтверждении» — курсивом в колонке менеджеров.

### Действия

- **«Это мои»** — менеджер, по выделенным строкам. Создаёт черновики.
- **«Отозвать»** — менеджер, только по своим незафиксированным.
- **«Зафиксировать»** — админ, кнопка видна только ему.
- **«Назначить направление»** — админ, по выделенным.

Без пакетных операций первичная разметка полутора тысяч поставщиков
невыполнима — это не удобство, а обязательное условие внедрения.

### Карточка справа

Добавляется шапка: бейдж направления, список закреплённых менеджеров со статусом
закрепления, строка «платили: …» с фактическими плательщиками и суммами;
незакреплённые в ней помечены предупреждением.

Вкладки «Структуры прайсов» и «Ручные привязки» не трогаем — они работают.

### Администрирование

Новый раздел «Закрепление поставщиков»: очередь черновиков с группировкой по
менеджерам, фиксация пачкой, справочник направлений, привязка менеджер →
направление, список нераспознанных `responsible`.

## 6. Первичное заполнение

Готового источника «поставщик → направление → менеджер» нет, поэтому:

1. Скрипт `server/tools/bootstrap_assignments.py` создаёт **черновики** по
   истории: менеджер получает черновик по поставщику, если на него приходится
   **не менее 20 % суммы оплат этому поставщику за последние 12 месяцев**.
2. Считаем по **сумме**, а не по количеству: количество перекошено мелкими
   регулярными платежами.
   Порог намеренно низкий, и по одному поставщику черновик получат несколько
   человек — так и задумано. Лишнее менеджер отзовёт сам за минуту, а вот
   пропущенного поставщика он в списке из полутора тысяч может не заметить
   вовсе. Ошибка в сторону лишнего дешевле ошибки в сторону недостающего.
3. Черновик — это предложение, а не назначение. Менеджер проверяет свой список,
   лишнее отзывает, недостающее добавляет.
4. Админ фиксирует пачкой по каждому менеджеру.
5. Направления проставляются автоматически при фиксации (раздел 2).

### Тесты, которые обязаны быть

- поставщик с двумя направлениями виден в обоих фильтрах и не задваивается в «Все»;
- разные написания одного менеджера из 1С дают одну позицию фильтра;
- поставщик без закрепления не пропадает из списка;
- менеджер не может править зафиксированное закрепление, админ может;
- заявленный поставщик попадает в фильтр «Мои» до фиксации;
- черновик чужого менеджера не попадает в мой фильтр «Мои», но виден в списке;
- фильтр по направлению не ограничивает выдачу — переключение показывает чужое;
- вкладка работает при недоступном сервере, кнопки закрепления заблокированы;
- миграция не теряет существующие карточки, структуры и привязки.

## 8. Внедрение

1. Выкатить с выключенным фильтром направления, прогнать первичное заполнение.
2. Неделя менеджерам на проверку своих черновиков.
3. Админ фиксирует; включаем фильтры по умолчанию.
4. Через месяц снять метрику: доля поставщиков с зафиксированным закреплением и
   доля оплат, прошедших от незакреплённых менеджеров.

## 9. Принятые решения

Записаны с основаниями: через полгода будет непонятно, почему сделано так, а
переспросить будет уже не у кого.

**1. Направление — умолчание фильтра, а не право доступа.** Менеджер видит
поставщиков всех направлений, но при открытии вкладки отобрано его собственное.
Скрывать чужое нельзя: чаще всего вкладку открывают с вопросом «не помню, чей
это поставщик», и жёсткое ограничение выдачи убило бы главный сценарий.

**2. Разделение по брендам внутри поставщика не хранится.** У «Суперкосметикс»
в карточке две фамилии без расшифровки, кто за какой бренд. Поле пришлось бы
заполнять руками при каждом закреплении, а в отборе и фильтрах оно не участвует.

**3. Заявленный поставщик — «мой» сразу.** Черновик попадает в фильтр «Мои» в
момент заявки, с пометкой «на подтверждении». Фиксация админом меняет не
видимость, а право на правку: иначе менеджер между заявкой и фиксацией остаётся
без собственного списка.

**4. Порог первичных черновиков — 20 % суммы за 12 месяцев.** По одному
поставщику черновик получат несколько человек, и это нормально: лишнее менеджер
отзовёт за минуту, а пропущенного поставщика в списке из полутора тысяч он может
не заметить вовсе.

### Открыто

**Перенос `suppliers.db` на сервер** — согласован принципиально, сроки не
определены. От разделов 1–8 не зависит, планируется отдельно.

## 10. Что показало внедрение

Развёрнуто 4 августа 2026. Миграция `004` применена, API пересобран, разметка
записана. Ниже — то, в чём боевые данные разошлись с планом.

**Правило разметки пришлось изменить прямо на проде.** По первоначальному
правилу (доля суммы за 12 месяцев) больше всего черновиков получали
офис-менеджер (81) и бухгалтер (70) — они проводят платежи по чужим заявкам и
поставщиков не ведут. Из 378 черновиков к делу относились 150. Кандидатом
теперь может быть только тот, у кого задано направление; отдельного поля
«должность» не понадобилось — направление есть ровно у категорийных менеджеров
и служит признаком само по себе.

Заодно изменился смысл доли: она считается от оплат категорийных менеджеров, а
не от всех подряд. Иначе поставщик, у которого девять десятых платежей провёл
бухгалтер, не дотянул бы до порога ни у кого.

**«Половина поставщиков у нескольких менеджеров» — миф.** Это утверждение
стояло в комментариях к коду и было одним из оснований делать связь
многие-ко-многим. На деле столько их только потому, что в оплатах видны и не
менеджеры. Среди категорийных менеджеров на 148 размеченных поставщиков общих
оказалось **два** («Мезон де Люкс» и «Суперкосметикс»). Связь всё равно
многие-ко-многим — эти два случая реальны, — но основание другое.

**Категорийных менеджеров восемь, а не двадцать два.** Из 23 учётных записей:
8 КМ (5 Beauty, 2 Fashion, 1 помощник Fashion), 6 уволившихся, остальные —
бухгалтерия, маркетинг, логистика, отдел развития. Направление проставлено
только восьмерым.

**Четверть истории оплат осталась без хозяина.** 1624 оплаты из 6966 записаны
на людей без учётной записи, из них 1268 — на одного уволившегося менеджера,
за которым числятся 172 поставщика. Их поставщики не получили ни одного
кандидата: в истории оплат за ними не стоит никого из работающих.

**Итог разметки:** 149 черновиков по 147 поставщикам у 8 менеджеров.
Направления: Beauty 110, Fashion 38. Без закрепления — 431 поставщик из 579;
это и есть ручная работа, и она больше, чем предполагалось планом.
