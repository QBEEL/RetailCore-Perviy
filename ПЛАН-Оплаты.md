## 1. Что в файле

`Для планирования/Оплата поставщикам.csv` — **6 929 строк, 16 колонок**, кодировка
**cp1251**, разделитель **`;`**, суммы с пробелом-разрядом и запятой-копейкой.

Это выгрузка **заявок на оплату** из 1С, а не платёжных документов. Разница важна:
у заявки есть своя дата, свой автор и свой статус согласования, а факт оплаты —
отдельные два поля.

### Пять находок, которые меняют устройство модуля

**1. «Номер» не уникален — он обнуляется каждый год.**
`IP00-000001` встречается 6 раз: 2021, 2022, 2023, 2024, 2025, 2026 — каждый раз
другой поставщик и сумма. По одному номеру 5 040 «лишних» строк.

Проверил ключи на всех 6 929 строках:

| Ключ | Уникальных | Коллизий |
|---|---|---|
| `Номер` | 1 889 | **5 040** |
| **`Номер` + `Дата заявки`** | **6 929** | **0** |
| `Номер` + `Дата заявки` + `Сумма` + `Получатель` | 6 929 | 0 |

Ключом дедупликации будет **`Номер` + `Дата заявки`** — минимальный из тех, что
дают ноль коллизий. Брать один `Номер`, как просится по названию, — значит при
импорте потерять 5 040 строк из 6 929.

**2. В файле уже есть будущее.** Даты платежей идут до **20.10.2026**, из них
**66 позиций позже сегодняшнего дня**. Календарь на первом запуске будет не
пустой — в нём сразу появится реальный план. Даты заявок доходят до 01.08.2026.

**3. Для заявок, созданных сегодня, 1С печатает только время.** Четыре строки
(`IP00-001273…001276`) имеют в «Дате заявки» значение вида `11:19`. Импорт будет
подставлять дату выгрузки файла. Если это не учесть, импорт падает — я на этом
уже споткнулся при анализе.

**4. Отсрочку надо считать по истории, а не только спрашивать.**
Вы предложили в профиле поставщика 7/14/30/60 дней. По факту разброс шире и
устойчив у каждого:

| Поставщик | Заявок | Медиана отсрочки |
|---|---|---|
| Сафило СНГ ООО | 309 | **34 дн** |
| НОСОВА ВИОЛЕТТА ИГОРЕВНА ИП | 172 | 23 дн |
| Дикси-Трейдинг ООО | 177 | 21 дн |
| НеваЛайн ООО | 265 | 19 дн |
| Юнайтед БТ ООО | 269 | 9 дн |
| ЗЕЛИНСКИЙ И РОЗЕН ПАРФЮМЕРИЯ ООО | 126 | 6 дн |
| Суперкосметикс ООО | 190 | 4 дн |

Медиана по всей базе — 6 дней. Поэтому: **посчитанная медиана — значение по
умолчанию, поле в профиле — ручное переопределение**. В карточке будет видно
и то и другое: «отсрочка 30 дн (вручную) · по истории 34 дн».

**5. Ваша цветовая шкала не разделит дни — она покрасит почти всё красным.**
Реальные суммы за день по 1 127 дням с оплатами:

| | |
|---|---|
| медиана дня | **1 432 829 ₽** |
| 75-й процентиль | 2 800 177 ₽ |
| 95-й процентиль | 6 569 611 ₽ |
| максимум | 15 910 902 ₽ |

По шкале 100k / 300k / 700k распределение выходит таким:

| Уровень | Дней | Доля |
|---|---|---|
| 🟢 до 100 тыс | 65 | 6 % |
| 🟡 100–300 тыс | 120 | 11 % |
| 🟠 300–700 тыс | 158 | 14 % |
| 🔴 700+ | **784** | **70 %** |

Семь дней из десяти красные — индикация перестаёт что-либо значить.
**Предлагаю шкалу 500 тыс / 1,5 млн / 3 млн**: она даёт 25 / 25 / 25 / 25 и
сразу показывает, какой день реально тяжёлый. Пороги вынесу в настройки, ваши
исходные оставлю как один из вариантов в один клик — **это решение №1 для вас**.

## 2. Как хранить

Отдельная база `payments.db` рядом с `suppliers.db` и `history.db` в `%APPDATA%`.
Не в существующие — у оплат свой жизненный цикл, свои миграции и свой объём.
Схема через `PRAGMA user_version`, как в `core/suppliers/schema.py`.

```
payments
  id                INTEGER PK
  doc_number        TEXT    -- «Номер»           ┐ вместе — UNIQUE,
  request_date      TEXT    -- «Дата заявки»     ┘ ключ дедупликации
  pay_date          TEXT    -- «Дата платежа», может быть пусто
  amount            REAL
  vat               REAL
  currency          TEXT
  supplier_id       INTEGER -- → suppliers.db, может быть NULL
  recipient         TEXT    -- «Получатель» как в 1С, всегда сохраняем
  status            TEXT    -- 5 наших статусов
  source_status     TEXT    -- «Статус» из 1С, как было
  paid_flag         INTEGER -- «Оплачена / Закрыта»
  operation         TEXT
  over_limit        INTEGER
  priority          TEXT
  edo_state         TEXT
  responsible       TEXT    -- «Заявитель»
  author            TEXT
  comment           TEXT    -- своё, 1С не заполняет
  had_files         INTEGER -- «Есть файлы» из 1С
  origin            TEXT    -- 'import' | 'manual' | 'order' | 'pricing'
  origin_ref        TEXT    -- ссылка на заказ/переоценку
  created_at, updated_at
  UNIQUE (doc_number, request_date)

payment_files      -- вложения, добавленные в приложении
  id, payment_id, path, name, size, added_at

budgets
  year, month, amount, note, updated_at
  PRIMARY KEY (year, month)

recipient_links    -- «Получатель» из 1С ↔ карточка поставщика
  recipient_key TEXT PK   -- нормализованное имя
  recipient     TEXT      -- как пришло
  supplier_id   INTEGER
  linked_by     TEXT      -- 'auto' | 'manual'

import_runs        -- журнал импортов
  id, path, file_hash, rows_total, rows_new, rows_updated,
  rows_skipped, started_at, finished_at, error
```

Индексы: `pay_date`, `supplier_id`, `status`, `(supplier_id, pay_date)`.

### Статусы

Ваши пять статусов кладутся на данные так:

| Статус | Откуда при импорте | Строк |
|---|---|---|
| **Оплачено** | `Оплачена = Да` | 6 721 |
| **Отменено** | `Статус = Отклонена` | 102 |
| **Запланировано** | не оплачена, дата платежа **≥ сегодня** | ~20 |
| **Просрочено** | не оплачена, дата платежа **< сегодня** | ~86 |
| **Перенесено** | только вручную, в 1С аналога нет | 0 |

Правило автопросрочки, которое вы задали, требует одной оговорки, иначе оно
испортит историю. **Просроченным становится только «Запланировано»**, у которого
дата ушла в прошлое. «Оплачено» и «Отменено» не трогаются никогда — иначе все
отклонённые заявки 2022 года на следующем открытии станут «Просрочено» и повиснут
в дашборде вечным долгом. «Перенесено» тоже не трогаем: перенос — это осознанное
решение человека, у него будет новая дата.

Пересчёт — при открытии модуля и при смене даты, не по таймеру.

### Получатель ↔ карточка поставщика

579 получателей в 1С — это юрлица (`ООО` 250, `ИП` 194, без формы 119, `АО` 10,
`ПАО` 5), а карточки в `suppliers.db` заведены по торговым именам. Сопоставление
будет двухступенчатым, ровно по образцу уже работающего `core/suppliers/links.py`:

1. нормализация — регистр, `NBSP`, двойные пробелы, отброс формы (`ООО`, `ИП`, `АО`…);
2. `rapidfuzz` по остатку с порогом, ниже порога — ручная привязка в UI.

В данных есть прямой мусор, который нормализация обязана съесть:
`'Домосканова\xa0Регина'` (NBSP), `'Л?вкина София'` (потерянная буква),
`'Харитонова  Елена Александровна ИП'` (двойной пробел).

**Непривязанный получатель не блокирует ничего** — оплата хранится и считается
по текстовому имени. Привязка нужна только для отсрочки и связи с заказами.

## 3. Импорт

`Импорт из 1С` в модуле оплат: выбор файла → разбор в фоне с прогрессом →
**предпросмотр** (новых / изменившихся / без изменений) → применение.

Правила:

* кодировка cp1251 с откатом на utf-8, разделитель определяется автоматически;
* `11:19` в дате заявки → дата изменения файла;
* суммы: `1 649 018,00` и `NBSP` → `1649018.00`;
* дедупликация по `(Номер, Дата заявки)` через `ON CONFLICT DO UPDATE`;
* **ручные правки не затираются**: если у записи `origin != 'import'` или
  заполнены `comment`/вложения/`Перенесено`, импорт обновляет только те поля,
  что пришли из 1С, и не сбрасывает своё;
* повторный импорт того же файла: 6 929 прочитано, 0 новых, 0 изменённых;
* каждый запуск пишется в `import_runs` с хешем файла — видно, что уже заливали.

## 5. Календарь

Месячная сетка 7×6. В каждом дне: сумма, количество платежей, список (первые
2–3 и «ещё N»), цветная полоса уровня. Клик по дню — панель со всеми платежами
дня, двойной клик по платежу — карточка. Перенос платежа перетаскиванием на
другой день, если это «Запланировано».

Под сеткой — строка бюджета месяца: `использовано / бюджет · остаток · %`.

Учитывая находку №5, цвет считается по настраиваемым порогам. Дни с
`Просрочено` помечаются отдельно рамкой, а не цветом суммы — иначе просрочка на
30 тыс. потеряется в зелёном.

## 7. Бюджет

Бюджет на месяц: сумма + заметка. Показываем использовано / остаток / процент,
предупреждение при превышении и при подходе к порогу (по умолчанию 90 %).

При установке бюджета подсказываем историю: средний и медианный расход этого
месяца за прошлые годы. Здесь стоит сказать прямо: **ваш пример «Август —
15 000 000 ₽» в 4 раза ниже факта** — август 2025 закрыт на 51,9 млн, медиана
месяца 57,4 млн. Если 15 млн — это реальный план на август 2026, предупреждение
о превышении сработает в первую же неделю. Скорее всего пример был условный, но
проверьте — от этого зависит, считать ли бюджет по всем оплатам или только по
части (**решение №4**).

Превышение не запрещает создавать оплаты — только предупреждает.

## 9. Автоматическое планирование

Считаем по каждому поставщику с достаточной историей и выдаём предложения:

| Правило | Как считаем | Порог |
|---|---|---|
| Обычная дата месяца | мода дня месяца | ≥ 5 оплат, доля моды ≥ 40 % |
| Регулярный платёж | медиана интервала, разброс | ≥ 4 оплаты, коэф. вариации < 0,35 |
| Рекомендуемая сумма | медиана последних 6 | разброс < 30 % |
| Давно не платили | дней с последней > 2,5 × медианы интервала | ≥ 3 оплаты |
| Отсрочка | медиана `дата платежа − дата заявки` | ≥ 3 оплаты |

Медиана вместо среднего сознательно: у Сафило 309 заявок с медианой 34 дня, но
есть выбросы до 303 дней — среднее по базе 11,5 против медианы 6, среднее врёт.

Предложения — **всегда предложения**: строка «Сафило СНГ: обычно 10-го числа,
~2,1 млн, последняя оплата 47 дней назад» и кнопка «Создать». Ничего не
создаётся само. Дата, попавшая на выходной, сдвигается на ближайший рабочий
день — в истории на выходные приходится 3 % оплат.

Уже видно, что сработает: у 6 из 10 крупнейших поставщиков медиана интервала
7–14 дней, а `НОСОВА ВИОЛЕТТА ИГОРЕВНА ИП` (172 оплаты) не оплачивалась с
25.06.2025 — это первое предупреждение, которое выдаст модуль.

## 11. Связь с заказом и переоценкой

На страницах «Заказ» и «Быстрая смена цен» появляется кнопка **«Создать оплату»**,
активная когда есть итоговая сумма и определён поставщик.

```
итог заказа / переоценки
        ↓
   «Создать оплату»
        ↓
поставщик подставлен, сумма подставлена,
дата = сегодня + отсрочка (профиль → иначе медиана истории)
дата на выходном сдвигается на рабочий день
        ↓
открывается календарь на этом месяце,
карточка заполнена и ждёт подтверждения
        ↓
origin='order', origin_ref = файл заказа
```

В профиль поставщика (`suppliers.db`) добавляется `payment_terms_days` —
переопределение отсрочки, варианты 7/14/30/60 и ручной ввод. Пусто = считать
по истории.

Запись не создаётся молча: карточка открывается предзаполненной, сохранение —
за пользователем.
