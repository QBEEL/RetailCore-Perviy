# RetailCore

RetailCore — приложение нового поколения для категорийных менеджеров и специалистов по управлению ассортиментом.

Система помогает автоматизировать ежедневные задачи:
- анализ товарных каталогов;
- поиск и сравнение товаров;
- сопоставление ассортимента разных брендов;
- выявление аналогичных продуктов;
- настройка параметров поиска под различные категории;
- подготовка данных для принятия закупочных решений.

RetailCore создан для того, чтобы сократить время на рутинный анализ и повысить эффективность работы с ассортиментом.

Технически это настольное приложение для Windows: берёт данные из
файла-каталога (артикул, EAN, цена) и проставляет их в целевую таблицу,
сопоставляя строки по идентификаторам, названию и объёму. Работает с любыми
брендами и любой структурой колонок — роли полей определяются автоматически
по заголовкам и содержимому файла.

> Проект раньше назывался Excel Data Matcher. При первом запуске новой версии
> настройки, история и журналы автоматически переезжают из
> `%APPDATA%\ExcelDataMatcher` в `%APPDATA%\RetailCore` — делать ничего не нужно.

## Запуск

**Готовое приложение:** `dist\RetailCore.exe` — один файл, Python и
библиотеки не нужны. Скопируйте его куда угодно и запускайте двойным кликом.

**Из исходников:** двойной клик по `start.bat`. При первом запуске создаётся
окружение `.venv` и устанавливаются зависимости (несколько минут). Ручной
запуск: `.venv\Scripts\python.exe run.py`

## Сборка

```
.venv\Scripts\python.exe tools\make_icon.py                 # иконка из app.svg
.venv\Scripts\pyinstaller.exe RetailCore.spec --noconfirm --clean
```

Проверка собранного файла без открытия окна — отчёт пишется в указанный файл:

```
"dist\RetailCore.exe" --selftest каталог.xlsx цель.xlsx отчёт.txt
```

## Возможности

**Сопоставление.** Этапы по убыванию надёжности: артикул → EAN → название с
объёмом → нечёткое сравнение названий. Объём проверяется как жёсткое условие с
допуском 5 %, поэтому строка на 50 мл не получит цену варианта на 10 мл.
Спорные случаи попадают в «Требует проверки» со списком вариантов вместо
молчаливой подстановки.

**Несколько каталогов.** Кроме основного прайса можно добавить дополнительные —
архивные за прошлые месяцы или прайсы других каналов. Каждый этап проходит по
всем каталогам сразу; при равной оценке побеждает тот, что выше в списке.
Колонка «Каталог» показывает, откуда взяты данные. Это закрывает позиции,
которых нет в текущем прайсе, — источником остаются ваши собственные файлы, а
не сторонние данные.

**Перенос заказа** (вкладка «Заказ»). Количества из выгрузки 1С переносятся в
бланк заказа поставщика. Лист и колонка определяются автоматически: из
нескольких колонок «Заказ» берётся та, где действительно есть числа
(в 1С такая колонка есть у каждого магазина). Оба выбора меняются вручную —
в книге с несколькими листами нужный указывается в списке «Лист», и этот выбор
запоминается для файла. Соответствие ищется по артикулу, затем по штрихкоду;
совпадение по названию автоматически не применяется — в бланке рядом стоят
обычная позиция и ТЕСТЕР, у которых артикулы отличаются одной буквой.

Колонка «Характеристика» из выгрузки 1С показывается рядом с наименованием и
участвует в подборе: у оттенков 01 и 02 название одинаковое, различает их именно
она.

Позиции, которых нет в бланке, показываются отдельным списком с похожими
строками (тестеры помечены) и выгружаются в отдельный файл. Нужную строку можно
найти поиском по всему бланку — по артикулу, штрихкоду, словам названия или с
опечаткой.

**Быстрая смена цен** (вкладка «Быстрая смена цен»). Готовит файл загрузки цен
в 1С по файлу переоценки поставщика. Раньше это делалось руками: выгрузить
шаблон, открыть прайс, найти товар, скопировать цену — и так несколько сотен
раз. Теперь нужно выбрать два файла и нажать «Сравнить».

Шаблон 1С разбирается по служебному листу книги, где 1С сама перечисляет номера
колонок каждого вида цены, — гадать по объединённой шапке не приходится, и
работают выгрузки с любым числом видов цен. Выгрузка приходит с расширением
`.xls`, хотя внутри это обычный xlsx; приложение открывает такие файлы по
содержимому, а не по имени.

Соответствие «вид цены 1С ← колонка поставщика» подбирается автоматически:
закупочные цены к закупочным, розничные к розничным, и внутри группы — та
колонка, что описывает новую цену, а не текущую. Выбор правится на странице и
сохраняется в **профиль поставщика**, который подбирается по имени файла, —
следующий прайс того же поставщика сопоставится сразу. Новый поставщик
подключается без правки кода.

Итоговый файл — это исходный шаблон, в котором изменены только колонки «Цена».
Оба листа, объединённая шапка, порядок и названия колонок, ширины, скрытые
служебные колонки, форматы чисел и стили остаются как были. Колонки «Изменение»
и «%» не трогаются намеренно: в шаблоне это формулы, и они пересчитаются сами.
По настройке строки, для которых новой цены нет, можно вообще убрать из файла —
нумерация «№» тогда пересчитывается.

**Артикулы с вариантами.** В выгрузке 1С одна ячейка артикула перечисляет
варианты одной номенклатуры — `zrp0050perG32/zrp0010perG32`, иногда через
обратный слеш, — и такая ячейка стоит сразу в нескольких строках, которые
различаются только объёмом в названии. Проверяется каждый артикул, а нужный
вариант выбирается по **ближайшему** объёму: допуска в 5 % мало, потому что
«195 мл» и «200 мл, банка» проходят его оба. При равном объёме решает сходство
названия. Поддерживается и обратная запись — `ABC123/50`, где после разделителя
стоит не другой артикул, а модификация: если точного совпадения нет, поиск идёт
по базовому артикулу. Разделители обоих видов задаются в настройках.

Нечёткое сравнение названий здесь никогда не применяется молча: когда артикула
у поставщика нет (позиция снята), похожие названия — это соседний аромат той же
линейки, и его цена ушла бы не туда. Такие строки попадают в «Требует
сопоставления» со списком вариантов, из которого нужный выбирается вручную;
можно и выгрузить их отдельным файлом, чтобы запросить у поставщика.

**База поставщиков** (вкладка «Поставщики»). У каждого поставщика свой прайс и
своя структура данных, поэтому приложение не сводит всех к одному формату, а
запоминает разбор каждого: какой лист читать, какая колонка заполняет какой вид
цены 1С и какие позиции пришлось свести вручную. Ручная работа не повторяется —
на разобранной паре файлов первый прогон дал 88 % сопоставления, второй с теми
же привязками 99 %.

Список отбирается по **направлению** (Beauty, Fashion) и по **менеджеру**.
Поставщик закрепляется за менеджером, а не вычисляется по оплатам: раньше
ведущим считался тот, кто чаще платил, и разовый платёж за коллегу записывал
человека в менеджеры навсегда. Менеджер отмечает своих поставщиков сам —
выделением в таблице и кнопкой **«Это мои»**, — а администратор подтверждает
их кнопкой **«Зафиксировать»**; после подтверждения снять закрепление может
только он. Заявленное считается своим сразу, не дожидаясь подтверждения, и
помечается в списке как «на подтверждении».

Менеджеров у поставщика может быть несколько: «Суперкосметикс» ведут двое по
разным брендам, и назначать единственного владельца было бы выдумкой. Кто
платил на самом деле, по-прежнему видно — строкой «платили» в карточке; если
среди плативших есть незакреплённый, карточка предупреждает об этом, но ничего
не блокирует.

Направление отбирает список, но ничего не прячет: менеджер Beauty может
переключиться на Fashion и найти чужого поставщика. Умолчание при открытии —
своё направление и свои поставщики. Отбор и сортировку по колонкам считает
сервер, список выдаётся страницами.

Поставщик узнаётся по нескольким признакам сразу: по имени файла, по
дополнительным именам из карточки и по набору заголовков прайса. Последнее
важнее всего — обезличенный `переоценка_09_2026.xlsx` всё равно опознаётся,
если структура файла та же. Подпись над соответствием колонок показывает, чем
именно он опознан. Структур у поставщика может быть несколько: прислал файл
другого формата — появится вторая, а первая останется.

Структура появляется сама после первого сравнения, но её можно добавить и
вручную — кнопка **«Добавить прайс»** в карточке поставщика. Это нужно в двух
случаях: завести поставщика заранее, до первой переоценки, и — чаще —
подключить к уже заведённому поставщику файл нового формата. Без этого
приложение такой файл не узнает и заведёт вторую карточку вместо того, чтобы
дополнить имеющуюся.

В том же окне правится **разметка колонок**: какая колонка прайса содержит
артикул, код, штрихкод, наименование, категорию, объём. Автоопределение
ошибается на нестандартных прайсах, а роль колонки решает, по чему вообще
ищется товар. Заданная разметка применяется при каждом чтении файлов этого
поставщика. Соответствие видам цен 1С задаётся здесь же и не обязательно —
при сравнении оно всё равно подбирается автоматически.

Привязка ключуется скрытыми колонками шаблона с идентификаторами номенклатуры и
характеристики — тем же, чем сама 1С опознаёт позицию у себя. Такой ключ
переживает переименование товара, смену артикула и новую выгрузку шаблона.
Артикул ключом быть не может: одна его ячейка стоит сразу в нескольких строках,
различающихся только объёмом, и привязка соседней строки применилась бы не туда.
Для выгрузок без идентификаторов есть запасные ключи — артикул с объёмом и
название.

Молчаливой привязка не бывает. В таблице она видна отдельным способом
(«Привязка»), а если за артикулом оказался товар с заметно другим названием —
рядом появляется предупреждение: поставщик мог отдать артикул другой позиции.
Снять привязку можно и на странице цен, и в карточке поставщика.

База лежит в `%APPDATA%\RetailCore\suppliers.db`. Профили, сохранённые до её
появления, переносятся при первом запуске автоматически.

После сравнения показываются всего товаров, найдено, не найдено, изменено цен,
без изменений и процент совпадения. Ход работы пишется в
`%APPDATA%\RetailCore\price.log`: какие файлы сравнивались, какое соответствие
колонок применялось и сколько строк не нашлось.

**Новинки и хиты.** После переноса приложение сообщает, сколько в прайсе позиций
с пометками поставщика — НОВИНКА, ХИТ, NEW, HIT, ЛИМИТКА, LIMITED — которых нет
в заказе. По кнопке «Новинки и хиты» открывается список: укажите количество, и
позиции добавятся в заказ и запишутся в бланк вместе с остальными. Пометка
ищется отдельными словами по всей строке прайса, поэтому «Новый артикул» и
«силиконовый» новинками не считаются.

**Исключения.** Номенклатура 1С и прайс поставщика описывают товар по-разному:
«Диффузор для ароматерапии Z&R Ветивер, Лимон» против «Диффузор. Средство для
ароматизации помещений Ветивер, Лимон (212,5мл)». Ручная привязка сохраняется
как исключение и применяется при следующих переносах раньше автоматического
подбора. Исключение хранит артикул, штрихкод и название, а не номер строки,
поэтому переживает новый бланк с другим порядком строк. Список правится по
кнопке «Исключения».

**Маркировка** (вкладка «Маркировка»). Коды DataMatrix разбираются на месте:
товар, серийный номер, повторы в пачке и испорченные коды видны без обращения к
«Честному ЗНАКу» и без входа. После входа по сертификату проверка спрашивает
систему, что она знает о каждом коде: чей он, в обороте ли, не выведен ли уже.
Проверка ничего не меняет в ГИС МТ, и других операций на вкладке пока нет.

**Поиск.** Частичные совпадения, любой регистр, лишние пробелы, поиск сразу по
нескольким словам и опечатки (rapidfuzz). Каждый результат получает оценку
Match Score с учётом веса поля: артикул важнее названия, название важнее
описания. Поля для поиска и их веса настраиваются.

**Таблицы.** Сортировка, фильтр по статусу, поиск с подсветкой совпадений,
изменение и скрытие колонок, копирование в буфер как TSV (Ctrl+C),
двойной клик — карточка товара.

Слой `core` не зависит от интерфейса и покрыт тестами:

```
.venv\Scripts\python.exe -m pytest tests -q
```

## Оплаты поставщикам

Вкладка `Оплаты` (`Ctrl+4`) работает с историей платежей и планом на будущее.
Внутри четыре вида одной и той же выборки: **Календарь**, **Таблица**,
**Аналитика** и **Бюджет**. Фильтр общий — иначе цифры на дашборде и в таблице
расходились бы, и объяснить это пользователю было бы нечем.

### Импорт из 1С

Источник — выгрузка «Оплата поставщикам» в CSV. Файл читается в cp1251, разбор
идёт в фоне, и до записи показывается предпросмотр: сколько строк новых,
сколько изменится, сколько останется как было.

Три особенности выгрузки учтены отдельно.

**Номер заявки обнуляется каждый год.** `IP00-000001` встречается и в 2021-м, и
в 2026-м — каждый раз другой поставщик и сумма. Записи опознаются по паре
«номер + дата заявки»: на 6929 строках она не даёт ни одной коллизии, тогда как
по одному номеру потерялись бы 5040 строк из 6929. Повторный импорт того же
файла создаёт ноль новых записей.

**Для заявок, созданных в день выгрузки, 1С печатает вместо даты только время**
(`11:19`). Такая ячейка читается как дата файла.

**Статус собирается из двух колонок** — согласования и отметки об оплате. Факт
оплаты сильнее согласования: в выгрузке есть заявки, помеченные оплаченными при
статусе «Не согласована».

Импорт не затирает то, что ввёл человек: комментарий, вложения и назначенный
вручную статус остаются на месте, обновляются только поля из 1С. Записи,
созданные в приложении, импорт не трогает вообще.

### План из Excel

Выгрузка 1С приносит **факт**. План приносят категорийные менеджеры — каждый в
своём файле. Кнопка `План из Excel` в шапке вкладки закрывает оба конца:
выдаёт единый шаблон и принимает заполненный.

**Шаблон.** Лист `План оплат`: дата, поставщик, сумма, ставка НДС,
комментарий. Поставщики и менеджеры подставляются выпадающим списком с листа
`Справочник` — он собирается из базы при выдаче шаблона. Список не
запрещающий: вписать поставщика, которого в базе ещё нет, можно, иначе нового
поставщика нельзя было бы запланировать вообще. Пустая ставка НДС читается как
22 % — план заполняют на будущие месяцы, а с 2026 года основная ставка эта.

**Загрузка.** Файл разбирается в фоне и ничего не пишет, пока человек не
подтвердит. В отчёте видно построчно: что появится, что изменится, что
исчезнет и что уже оплачено. Строка узнаётся по паре «поставщик + дата», сумма
в ключ не входит — исправленная сумма показывается как изменение, а не как
удаление с созданием.

**Замена, а не добавление.** Присланный файл — полная картина месяца, а не
добавка к прошлой: план менеджера за встреченные в файле месяцы заменяется
целиком. Иначе оплата, которую менеджер из плана убрал, осталась бы в
календаре навсегда — вычёркивать её пришлось бы руками тому, кто грузит файлы.
Месяцы берутся из дат строк, а не из шапки: строка, поставленная на соседний
месяц, входит в замену наравне с прочими и не задваивается при следующей
загрузке.

**Что не трогается.** Оплаченное и отменённое — никогда: факт сильнее плана,
и строка плана, ставшая оплатой, считается исполненной. Не трогаются и оплаты
из 1С, заведённые вручную и планы других менеджеров: замена ищет только записи
с меткой `plan:<год-месяц>:<менеджер>`, которую ставит сама загрузка.

Загруженные строки становятся обычными оплатами со статусом «Запланировано»:
видны в календаре, переносятся перетаскиванием, попадают в графу «Предстоит»
бюджета месяца. Источник у них — «План из Excel».

В общей базе действует то же правило, что и при создании оплаты вручную: план
на чужое имя загружает только администратор. Отказ приходит до разбора файла,
а не после нажатия «Применить».

### Статусы

| Статус | Когда |
|---|---|
| **Оплачено** | в 1С стоит отметка об оплате |
| **Запланировано** | не оплачено, дата не прошла |
| **Просрочено** | было «Запланировано», дата ушла в прошлое |
| **Перенесено** | дату сдвинул человек — перетаскиванием в календаре |
| **Отменено** | заявка отклонена в 1С |

Просроченным становится **только** «Запланировано». «Оплачено» и «Отменено» не
пересчитываются никогда: иначе отклонённые заявки прошлых лет при первом же
открытии стали бы просрочкой и повисли в дашборде вечным долгом.

### Календарь

Месячная сетка. В каждом дне — сумма, количество платежей и первые получатели.
Цвет показывает нагрузку дня, просрочка помечается **рамкой**, а не цветом:
иначе просроченные тридцать тысяч потерялись бы в спокойном зелёном дне.

Пороги цвета настраиваются (`Настройки` → `Оплаты`). Значения по умолчанию —
500 тыс / 1,5 млн / 3 млн — подобраны по фактической истории: медиана дня с
оплатами около 1,4 млн, и шкала в сотнях тысяч покрасила бы красным семь дней
из десяти. Есть готовые наборы порогов для другого масштаба оборота.

Оплаты переносятся на другой день перетаскиванием. В списке дня справа можно
выделить одну или несколько (Ctrl, Shift) и перетащить их вместе; перетаскивание
самой клетки переносит весь день и спрашивает подтверждение. Переносится только
неоплаченное — оплаченное и отменённое из выделения пропускается.

### Аналитика

Плитки: бюджет месяца, оплачено, осталось оплатить, просрочено, количество
оплат, средний платёж, крупнейший платёж, самый загруженный день.

Четыре графика на QtCharts (входит в PySide6): расходы по дням, по поставщикам,
по месяцам и распределение бюджета. Если бюджет месяца не задан, последний
график показывает структуру расходов по поставщикам.

Графики отвечают на действия. Наведение подсвечивает столбец и показывает
точную сумму, количество платежей и прирост к предыдущему периоду. Щелчок по
поставщику отбирает его платежи в таблице, щелчок по дню или месяцу переводит
календарь на эту дату. Сектор круговой диаграммы приподнимается под курсором.

На графике по дням оплаченное и предстоящее нарисованы разным цветом: отрезок
захватывает и прошлое, и будущее, а это разные вещи. Значения на осях
сокращены до миллионов — подписи вида «12147620» занимают половину графика и
всё равно не читаются; точное число даёт подсказка.

Подписи оси у графика по дням скрыты намеренно. `QBarCategoryAxis` делит ширину
на число категорий и обрезает текст под получившийся слот: на сорока пяти днях
от «30.06» остаётся одна точка. Прореживание не помогает — ось склеивает
одинаковые названия и теряет вместе с ними столбцы. Точки вместо дат хуже
честно пустой оси: отрезок назван в заголовке, дата — в подсказке.

Рейтинг получателей — с объёмом, средней и крайними суммами, ритмом оплат,
отсрочкой, привычным числом месяца и днями тишины.

Почти все показатели считаются по медиане, а не по среднему. Причина в данных:
отсрочка по базе имеет среднее 11,5 дня при медиане 6 — несколько заявок с
отсрочкой в десять месяцев тянут среднее вверх и делают его бесполезным для
подсказок.

Общий «средний интервал между оплатами» считается по поставщикам, а не по базе:
платежи идут почти каждый день, и промежуток «по базе» вырождается в единицу
независимо от того, как платят конкретному поставщику.

### Бюджет

Бюджет задаётся на месяц. Видно оплачено, предстоит, использовано, остаток и
процент исполнения; превышение и приближение к порогу подсвечиваются. При вводе
подсказывается, сколько уходило в этом месяце прошлых лет.

В расчёт входят **только** оплаты поставщикам: налоги, аренда и зарплата в
выгрузке есть, но к закупке отношения не имеют. Превышение не запрещает
создавать оплаты — оно предупреждает.

Платежи без даты платежа (незавершённые заявки прошлых лет) в бюджет и
календарь не попадают, но их сумма показана на дашборде отдельной строкой —
чтобы они не потерялись молча.

### Автопланирование

Приложение ищет закономерности в истории и **предлагает** — никогда не создаёт
само.

| Правило | Как считается |
|---|---|
| Регулярный платёж | медиана промежутка; ритм признаётся, если в ±50 % от неё укладывается больше половины промежутков |
| Давно не оплачивался | тишина превысила 2,5 медианных промежутка, но не больше 120 дней |
| Рекомендуемая сумма | медиана последних шести оплат, если разброс меньше 30 % |
| Обычная дата | мода числа месяца при доле не ниже 40 % |

Регулярность измеряется долей промежутков, а не коэффициентом вариации: у 136
получателей с достаточной историей медианный коэффициент вариации равен 0,93, и
порог «не больше трети» пропускал ровно двоих — при том что платят им явно
ритмично. Один сдвинутый на месяц платёж раздувает отклонение, но ритма не
отменяет.

Потолок тишины нужен по той же причине: в базе есть получатели, которым не
платили свыше четырёх лет. Это не просрочка, а закончившееся сотрудничество, и
предупреждать о нём — засорять список. Без потолка предупреждений было 180,
с ним — 26.

Дата, попавшая на выходной, сдвигается на ближайший рабочий день: в истории на
субботу и воскресенье приходится около трёх процентов оплат.

### Получатель и карточка поставщика

В 1С получатель записан юрлицом («НеваЛайн ООО»), а карточка поставщика
заведена под торговым именем. Нормализация снимает организационную форму,
неразрывные пробелы и сдвоенные пробелы, после чего имена сравниваются.

Автоподбор применяет только уверенные совпадения. Порог проверен на 578
получателях выгрузки: при 88 и выше есть одна пара разных юрлиц, при 85 — уже
пять («Кларис ООО» и «Кларис-2», два разных ИП с похожими фамилиями).
Остальное разбирается вручную кнопкой «Привязать получателей».

Сравнение идёт по `token_sort_ratio`, а не `token_set_ratio`: последняя считает
подмножество полным совпадением и даёт 100 для пары «ЗВЕЗДА» — «Звезда
Востока». Для юрлиц это готовая неверная привязка.

Непривязанный получатель ничего не блокирует: оплата считается по текстовому
имени. Привязка нужна для отсрочки и связи с заказами.

### Из заказа и переоценки — в оплату

На страницах `Заказ` и `Быстрая смена цен` есть кнопка **«Создать оплату»**.
Открывается вкладка оплат и карточка новой записи: поставщик подставлен, дата
посчитана по отсрочке.

Отсрочка берётся из карточки поставщика (`7` / `14` / `30` / `60` дней или своё
число), а если там ничего не задано — считается по истории оплат этому
получателю. В карточке видно и то и другое: «30 дней · по истории оплат: 19 дн».

Ни заказ, ни переоценка не считают денег: заказ переносит количества,
переоценка меняет цены. Сумма подставляется как медиана прошлых оплат, и в
комментарии прямо написано, что это медиана и её надо проверить по счёту.
Запись не создаётся молча — сохранение остаётся за пользователем.

### Таблица оплат

Поиск по поставщику, номеру заявки, комментарию и ответственному; фильтры по
периоду, статусу, сумме, ответственному и операции; сортировка по любой
колонке; массовое изменение статуса, даты и ответственного для выделенных
строк; экспорт в Excel — суммы выгружаются числами, чтобы по ним считался итог.

Отменённые платежи не входят в суммы: иначе на одном экране получались бы две
несходящиеся цифры — итог таблицы и объём выборки.

### Общая база: оплаты видят все

Раньше оплаты жили только на том компьютере, где их заполняли, и остальные
категорийные менеджеры их не видели. Теперь база общая — на сервере.

При первом открытии раздела «Оплаты» приложение спросит логин и пароль. Их
выдаёт администратор; при первом входе приложение потребует заменить выданный
пароль на свой — до этого записи в журнале не доказывают, кто именно правил
оплату.

**Что можно и чего нельзя.** Видно всё: чужие оплаты, календарь, аналитику и
бюджет отдела. Править можно только свои — те, где ответственным в выгрузке 1С
стоите вы. Чужая оплата открывается на просмотр: поля заблокированы, и в
карточке написано, за кем она закреплена.

Отдельные права у администратора: он заводит учётные записи, задаёт бюджеты,
загружает выгрузку из 1С (она обновляет оплаты всего отдела, поэтому доступна
не каждому) и может работать на локальной базе с последующей выгрузкой.

Каждое изменение попадает в журнал — кто, когда и какое поле поменял. Импорт
записывается одной строкой на прогон, а не на каждую из семи тысяч оплат.

**Если сервер недоступен**, вход можно пропустить: приложение покажет вашу
локальную базу и продолжит работать, как до появления общей.

### Локальная база и выгрузка на сервер

Администратор может работать на своей базе, не выходя из учётной записи:
прогнать у себя выгрузку 1С и присланные планы, посмотреть, что вышло, и
только потом отдать отделу. Переключатель — под названием программы слева;
в локальном режиме он жёлтый, чтобы забыть о нём было нельзя. Выбор
запоминается между запусками: молча вернуть человека в общую базу опаснее, чем
оставить его в своей — второе он хотя бы видит.

Вход при этом сохраняется. Локально работают только оплаты: поставщики,
закрепления, отчётность и личный кабинет остаются общими, и переключаться
ради них не приходится.

**Выгрузка** — в том же меню. Приложение сравнивает базы и показывает, что
уйдёт: сколько новых, сколько обновится, какие записи разошлись и чем именно.
Отправка идёт частями по 500 строк, каждая — транзакцией на сервере; оборванная
на середине выгрузка не портит базу, повторная догоняет остаток.

Три правила, по которым она работает.

**Сливает, а не зеркалит.** Записи, которых нет у вас, но есть на сервере, не
трогаются никогда: пока вы работали у себя, отдел работал в общей базе.

**Расхождение решается в пользу локальной записи** — выгрузку делает тот, кто
эти данные и готовил. Все расхождения перечислены в отчёте до записи.

**Запись узнаётся по своему ключу, смотря откуда взялась.** Строки из 1С — по
паре «номер заявки + дата заявки», тому же ключу, по которому работает импорт.
План из Excel — по метке плана, поставщику и дате. У созданных вручную ключа
нет вовсе, и берётся получатель, дата и ответственный; сумма в ключ не входит
намеренно — иначе исправленная сумма легла бы на сервер вторым платежом того же
дня и удвоила бы его в бюджете.

Вместе с оплатами уходят бюджеты месяцев — те, что у вас заданы и отличаются от
серверных.

### Вход и личный кабинет

Работать без входа нельзя: программа знает, кто правит общие оплаты и за кем
закреплены поставщики, и «неизвестный пользователь» ей не подходит. Окно входа
появляется до главного, отказ закрывает программу.

Пароль спрашивают не каждый запуск. Токен живёт двенадцать часов и сохраняется
в `%APPDATA%\RetailCore\session.json`; пока он действует, программа открывается
молча. **Пароль не сохраняется никогда** — украденный файл профиля даёт доступ
до конца дня, а не навсегда.

Если сервер недоступен, а вход был не позже недели назад, программа предложит
**продолжить без сервера**. Сопоставление, заказ, переоценка, каталог и история
работают как обычно — им сервер не нужен, и останавливать их из-за чужой аварии
незачем. Оплаты, поставщики, отчётность и администрирование закрыты до входа.
Неделя считается от последнего удачного входа; после неё пароль обязателен.

**Личный кабинет** (`Ctrl+P`, кнопка с вашим именем внизу меню): ФИО, логин,
права, направление, ваши имена в выгрузке 1С, адрес сервера и срок действия
входа. Там же — сколько поставщиков за вами закреплено, сколько ваших заявок
ждёт подтверждения и скольким чужим поставщикам вы платили. Оттуда же меняется
пароль и выполняется выход.

### Администрирование

Раздел появляется в меню только у администратора и только после входа в общую
базу. В нём заводятся и правятся учётные записи, назначаются новые пароли и
читается журнал изменений.

Ключевая настройка учётки — список имён из 1С. По нему считается, какие оплаты
человек вправе править. Один и тот же менеджер встречается в выгрузке под
несколькими написаниями — отметить нужно все, иначе часть его оплат окажется
для него чужой.

Вторая настройка — **направление** (Beauty, Fashion). Оно отмечается у тех, кто
ведёт поставщиков, и служит признаком категорийного менеджера: только таким
предлагается закрепление, и только они попадают в отбор вкладки «Поставщики».
Отдельного поля «должность» нет намеренно — бухгалтерия, маркетинг и логистика
оплаты проводят, но поставщиков не ведут, и без этого признака первичная
разметка предлагала им сотню чужих поставщиков.

Вкладка **«Закрепление поставщиков»** — очередь заявок: что менеджеры отметили
своим и ждёт подтверждения. Выделенные строки фиксируются одной кнопкой;
отклонённая заявка просто исчезает, и менеджер может подать её снова. Снять
уже зафиксированное закрепление можно там же, во вкладке «Поставщики».

Пароль показывается один раз, при создании учётки или при назначении нового.
В базе хранится только хеш: забытый пароль не восстанавливается, назначается
новый.

Вкладка **«Обслуживание»** удаляет данные общей базы: все оплаты вместе с
вложениями, бюджетами, журналом импортов и привязками получателей — у всех
менеджеров сразу. Нужно это, когда выгрузку из 1С переносят заново и
накопленное с ней уже не сходится: дописывать такую выгрузку к старой
бессмысленно.

Учётные записи, направления, закрепление поставщиков и журнал изменений при
этом остаются — восстанавливать их руками дольше, чем повторить импорт, и сама
запись об удалении попадает в журнал. Перед удалением видно, сколько чего
сотрётся, а подтверждений два: слово «УДАЛИТЬ» набирается руками, и следом
спрашивается пароль. «Да» в обычном вопросе нажимается не глядя, а отменить это
действие нечем — данные вернутся только из ночной резервной копии сервера.

На вкладке «Оплаты» под заголовком появляется предупреждение, если вы платили
поставщикам, за которыми не закреплены. Это не запрет — подменить коллегу в
отпуске обычное дело, — но чаще признак того, что поставщика забыли отметить
своим.

### Где лежит

**Общая база** — на сервере, вместе с вложениями; резервная копия снимается
каждую ночь. Скачанные вложения кэшируются в
`%APPDATA%\RetailCore\payment_cache\`.

**Локальная база** — `%APPDATA%\RetailCore\payments.db`: оплаты, бюджеты,
привязки получателей и журнал импортов. Используется, если вход в общую базу не
выполнен. Вложения — в `%APPDATA%\RetailCore\payment_files\`: ссылка на
исходник ломается, как только письмо переложат. Журнал импортов —
`payments.log`.

Серверная часть и её развёртывание описаны отдельно — [server/README.md](server/README.md).

## Маркировка «Честный ЗНАК»

Вкладка `Маркировка` (`Ctrl+M`) отвечает на вопрос «что это за коробка
приехала»: коды со сканера разбираются на месте, а после входа по сертификату
их можно спросить у самой системы.

### Что делает вкладка

1. **Разбор кодов.** Коды сканируются или вставляются списком — по одному в
   строке; список берётся и из файла (`.txt`, `.csv`). Плитки показывают,
   сколько кодов набрано, сколько за ними товаров, сколько кодов не разобралось
   и сколько экземпляров встретилось дважды. Всё это считается без сети и без
   входа: повтор серийного номера — это либо пересчёт, либо копия кода, и
   замечается он здесь же. Криптохвост отделяется от кода идентификации сам,
   даже когда сканер не выдал ни одного разделителя, — поэтому один и тот же
   экземпляр, снятый сканером и вставленный из таблицы, считается одним.
2. **Вход.** Контур (песочница или боевой) и сертификат из личного хранилища;
   вход подписывает КриптоПро. Смена контура сбрасывает вход: токен выдан для
   своего контура. По умолчанию выбрана песочница, боевой выбирается вручную и
   помечен цветом.
3. **Организация.** Сертификат по машиночитаемой доверенности действует за
   нескольких участников оборота, и система не выбирает за нас: боевой контур
   отвечает «Невозможно однозначно определить под какой организацией
   выполняется авторизация. Укажите запросе INN». На такой отказ вкладка
   открывает окно выбора, а не показывает текст, из которого непонятно, что
   делать. Список отдаёт ГИС МТ, выбранная организация запоминается — следующий
   вход идёт без вопросов, а сменить её можно кнопкой «Организация». Если
   справочник недоступен, ИНН вводится руками: без него вход невозможен вовсе,
   и упираться в чужую недоступность он не должен.
4. **Проверка.** В запрос уходит код идентификации без криптохвоста — с
   подписью система отвечает отказом. «Честный ЗНАК» отвечает по каждому коду:
   товар, состояние, владелец. Чужой код (владелец не совпал с ИНН сертификата) помечается
   отдельно, а переключатель «Только замечания» оставляет в таблице то, из-за
   чего стоит остановиться. Ответы запоминаются; галочка «Спросить заново»
   выключает подстановку — состояние кода меняется, и вчерашнее «в обороте»
   ничего не говорит о сегодняшнем. Испорченные коды в запрос не уходят.
5. **Журнал.** Что и когда спрашивали. Операции, ждущие ответа ГИС МТ, помечены
   прямо — опрос их состояния пока не подключён (см. «Чего ещё нет»).

Модуль `app/core/marking` — то же самое без интерфейса: разбор кодов, подпись,
вход, проверка кодов, чтение УПД, сверка, выгрузка в 1С и журнал операций.

### Сверка кодов маркировки

Подвкладка `Сверка кодов маркировки` отвечает на вопрос приёмки: то ли приехало,
что написано в документе. Ни сертификат, ни сеть для неё не нужны — обе стороны
сравнения лежат на этом компьютере.

1. **Документ.** Кнопка «Загрузить УПД» берёт тот самый XML, что пришёл по ЭДО:
   он лежит в папке с документом рядом с печатной формой. Архив, скачанный из
   Диадока целиком, тоже подходит — нужный файл в нём находится сам, по имени
   или по наличию таблицы товаров. Читаются версии формата 5.01–5.03, кодировка
   берётся из объявления в файле, а не угадывается: cp1251, прочитанный как
   utf-8, даёт не ошибку, а мусор вместо названий.
2. **Сканирование.** Код приходит в поле сам, по `Enter` от сканера. Ответ —
   широкой цветной плашкой: зелёное значит «клади», красное значит
   «остановись». Расхождение ещё и слышно — вещь в руках, и смотреть на экран
   после каждой некогда (звук отключается галочкой). Сканер стреляет по соседней
   коробке чаще, чем хотелось бы, поэтому есть «Отменить скан».
3. **Что с чем сравнивается.** В документе лежит код идентификации — товар и
   серийный номер, 31 знак. Сканер отдаёт то, что напечатано на этикетке: тот же
   код плюс криптохвост, а разделители полей теряются по дороге — их срезает и
   драйвер сканера, и поле ввода. Поэтому сравнение идёт по разобранному коду:
   пара «GTIN и серийный номер» у одной и той же вещи совпадёт всегда, как бы её
   ни сняли.
4. **Что видно сразу.** Повторный скан не засчитывается вторым экземпляром.
   Лишний код отличает «этот товар, но экземпляр не из документа» от «такого
   товара в документе нет» — с поставщиком это разные разговоры. Коды, записанные
   в документе дважды, и нехватка кодов против количества товара замечаются до
   всякого сканирования: это ошибки самого документа, и недостачей нашего товара
   они не являются.
5. **Акт сверки** (`.xlsx`) — для разговора с поставщиком и для приложения к
   претензии. В нём и то, чего не хватило, и то, что приехало сверх документа, а
   не только итоговое «не сошлось».
6. **«Спросить „Честный ЗНАК“»** переносит коды документа на вкладку проверки.
   Сверка и проверка отвечают на разные вопросы, и один без другого неполон:
   сверка говорит, что приехало ровно то, что в документе, а «Честный ЗНАК» — что
   эти коды в обороте и принадлежат поставщику.

Сверка ничего не отправляет в ГИС МТ и не заменяет приёмку по ЭДО: перевод
товара на наш баланс делает подписание УПД в Диадоке. Смысл в том, чтобы
расхождения нашлись **до** подписания, пока их ещё можно вернуть поставщику.

### Выгрузка кодов в 1С

Последний шаг приёмки: сверенные коды нужно завести в 1С штрихкодами
номенклатуры. Обработка загрузки ждёт три колонки — код номенклатуры,
характеристику и сам код, — а в УПД нет ни одной из них: поставщик пишет своё
название и свой GTIN. Чем одно связано с другим, знает только выгрузка
номенклатуры из 1С, и её нужно загрузить кнопкой «Номенклатура 1С».

**Что нужно в выгрузке.** Название, код номенклатуры и характеристика; штрихкод
— если он там есть. Колонки узнаются по шапке в любом написании
(«Номенклатура» / «Наименование» / «Товар»), шапка ищется в первых пятнадцати
строках — заголовок отчёта и период над ней не мешают. Путь запоминается, и при
следующем открытии вкладки файл перечитывается сам: номенклатура меняется, и
держать в памяти вчерашнюю значило бы однажды не найти заведённый утром товар.

**Как строки ложатся на номенклатуру** — по убыванию надёжности, и способ виден
в колонке «Номенклатура 1С»:

| Способ | Когда | Цвет |
|---|---|---|
| Привязано вручную | этот GTIN уже привязывали раньше | синий |
| По штрихкоду | в выгрузке есть штрихкоды, и GTIN из УПД нашёлся | зелёный |
| По названию | названия совпали слово в слово | зелёный |
| Похоже — подтвердите | точного совпадения нет, есть близкие | оранжевый |
| Не найдено | похожего тоже нет | красный |

Названия совпадают потому, что 1С дописывает к номенклатуре единицу измерения
(«…, шт»), а поставщик — нет; она отбрасывается с конца, и на живой поставке так
сошлись все сорок две позиции.

**Похожее само не применяется.** Молча подставить не ту номенклатуру значит
завести коды чужому товару, а находится это не раньше инвентаризации. Поэтому
близкие названия показываются подсказкой, а решение остаётся за человеком:
двойной щелчок по строке открывает выбор номенклатуры с поиском по всей
выгрузке. **Выбранное запоминается по коду товара** и на следующей поставке не
спрашивается — там же его можно и снять.

**Файл для 1С** — xlsx с тремя колонками шаблона, по строке на каждый код.
Только xlsx, и это не лень: код маркировки — строка из набора GS1, а в нём есть
и точка с запятой, и кавычка (в живой поставке встретились обе). В csv такую
строку приходится экранировать, и достаточно одной обработки, читающей файл
простым разделением по «;», чтобы половина кодов приехала в 1С обрезанной —
молча и без единой ошибки при загрузке.

По умолчанию берутся **только сверенные коды**: код из документа, которого не
нашлось на товаре, — это вещь, которая не приехала, и заводить ей штрихкод
значит поставить в 1С на приход то, чего нет. Галочка снимается, если нужен весь
документ. Строка без номенклатуры в файл не попадает, и сколько кодов не попало
— говорится прямо: загруженная половина выглядит в 1С ровно как загруженное
целиком.

### Станция управления заказами (СУЗ)

Коды выдаёт не ГИС МТ и не True API, а третья система — СУЗ. Она узнаёт
устройство по реквизитам из личного кабинета:

| Реквизит | Что это | Куда уходит |
|---|---|---|
| **ОМС ID** | какая станция обслуживает участника оборота | в каждый запрос, параметром |
| **Токен** | чем устройство подтверждает, что оно и есть оно | в каждый запрос, заголовком `clientToken` |
| **Идентификатор соединения** | какое устройство обращается | только в запрос токена |

**Токен живёт десять часов.** Это не наша оценка — так написано в инструкции
ЦРПТ, которая лежит в папке программы ПРИНТМАРКИ. Отсюда всё устройство: хранить
токен между запусками можно, полагаться на то, что он ещё жив, — нельзя.

**Переносить его из другой программы не нужно, и продлевать руками тоже.** У СУЗ
есть собственный вход по усиленной квалифицированной подписи, устроенный так же,
как в True API: `/auth/key` → подпись → `/auth/simpleSignIn` → токен. Кнопка
«Получить токен» проходит этот путь сертификатом, выбранным выше на той же
вкладке. А на отказ «Проверка учетных данных УОТ не пройдена» приложение
добывает новый токен само и повторяет запрос — один раз: если и свежий токен
отвергнут, дело не в сроке, а в правах, и крутить цикл незачем.

Подсказка под полями всегда показывает, сколько токену осталось. Знать это
заранее нужно затем, чтобы обновление не случилось посреди работы и не вызвало
неожиданный вопрос о пароле к контейнеру.

Кнопка «Проверить соединение» спрашивает у СУЗ `ping` — метод ничего не
заказывает и не тратит ни одного кода, поэтому проверять связь можно сколько
угодно. Полученный токен проверяется сразу: подойти ко входу он мог, будучи
выдан участнику, а не той станции, чей ОМС ID вписан, и узнать это лучше сейчас,
чем на первом заказе. Удачная проверка заодно сохраняет реквизиты — иначе
настроенное соединение не пережило бы перезапуск.

Отличий от входа в ГИС МТ три, и каждое видно на экране:

- **Токен хранится между запусками.** Не в `settings.json`, а в отдельном
  `marking_suz.json` с ограниченными правами: `settings.json` копируют и
  пересылают, а токен СУЗ равносилен доступу к заказу кодов от имени
  организации. На экране он показан огрызком вида `eyJh…ture` — по началу и концу
  видно, тот ли токен вписан, а воспользоваться показанным нельзя. Токен без
  отметки времени выдачи считается протухшим: перенесённый из другой программы
  мог быть выдан вчера.
- **Наборов два.** Устройство в песочнице и устройство в бою — разные, поэтому
  файл хранит два независимых набора, а переключение контура показывает другой.
- **Адрес можно вписать свой.** Встроены адреса облачной СУЗ — оба проверены
  обращением. Поле «Адрес СУЗ» существует ради локальной станции: она стоит в
  сети предприятия, и её адрес приложение знать заранее не может.

Проверка кодов и вход по сертификату от реквизитов СУЗ не зависят и наоборот:
это разные системы и разные способы представиться.

### Заказ кодов

Вкладка «Маркировка» разделена на две подвкладки, и это не оформление: работы
здесь две, и они не пересекаются. **Проверка кодов** идёт через ГИС МТ по
сертификату, **заказ кодов** — через СУЗ по её реквизитам. Держать обе половины
перед глазами значит каждый раз выбирать, какая сейчас не нужна.

Карточка «Заказы кодов» показывает, что заказано и **сколько кодов ещё можно
забрать**. Смотрят именно на последнее число: «сколько заказывали» на вопрос
«хватит ли» не отвечает — часть кодов давно забрана из буфера.

Новый заказ собирается там же: товарная группа, способ выпуска, контактное лицо
и строки «код товара — количество».

**Шаблон кода выбирается из тех, что подходят группе.** У каждой товарной группы
свой набор шаблонов, и чужой СУЗ отвергает прямо: «Для данной товарной группы
"Духи и туалетная вода" невозможно использовать выбранный шаблон КМ 10».
Справочник взят из руководства программиста СУЗ-Облако (раздел «Шаблон КМ») —
духи 9, лёгкая промышленность 10, обувь 1, молоко 20, косметика 46 или 47.

Номер сам по себе не значит для человека ничего, поэтому в списке написано то,
чем шаблоны на самом деле различаются: **длина серийного номера и наличие
криптохвоста**. Именно этим отличаются 46 и 47 у косметики, и выбрать между ними
по числу было бы гаданием.

Справочник — основание, но не последняя инстанция. Если СУЗ однажды приняла
шаблон, которого в руководстве нет, он остаётся в списке с пометкой «из вашего
заказа по этой группе»: реальность старше документа. Способ оплаты справочника
не имеет — он зависит от договора с ЦРПТ и берётся из прошлого заказа.

| Способ выпуска | Код в запросе |
|---|---|
| Маркировка остатков | `REMAINS` |
| Производство в РФ | `PRODUCTION` |
| Ввезен в РФ (Импорт) | `IMPORT` |
| Перемаркировка | `REMARK` |
| Принят на комиссию от физического лица | `COMMISSION` |
| Маркировка вне производства или импорта | `REAPPLY` |

Названия дословно те, что показывает ПРИНТМАРКИ — программа, которой отдел
пользуется давно. Одно и то же в двух программах должно называться одинаково,
иначе однажды будет выбрано не то. Производство и импорт требуют сведений о
производственной площадке; они пока не подключены, и вкладка говорит об этом
прямо, а не отправляет заказ, который ЦРПТ отклонит.

**Заказ — единственная операция во всём приложении, которая тратит деньги**, и
устроена она соответственно:

- **Заказ подписывается.** Открепленной подписью — ровно наоборот, чем вход, где
  СУЗ и ГИС МТ требуют присоединённую. Без подписи ответ прямой: «Не указано
  значение параметра "Открепленная подпись в формате Base64"». Подпись уходит
  заголовком `X-Signature` и считается по тем же байтам, что уходят в тело, —
  для этого тело собирается один раз и передаётся готовой строкой, а не
  собирается второй раз внутри транспорта.
- **Проверки до сети.** Количество на товар — от 1 до 2 000 000; границу назвала
  сама СУЗ, отвечая на заказ с нулём. ПРИНТМАРКИ держит свой, более строгий
  предел в 150 000, но это её ограничение, а не системы, и выдавать его за общее
  значило бы запрещать разрешённое. Запрет на одинаковые коды товаров в заказе —
  оттуда же, из её проверок.
- **Подтверждение всегда**, даже в песочнице. Привычка нажимать не глядя
  вырабатывается именно там, а срабатывает потом в бою. В окне показано ровно
  то, что уйдёт в запрос; кнопка подтверждения не назначена кнопкой по
  умолчанию, чтобы Enter по привычке не заказывал коды.
- **Повторов ноль.** Транспорт повторяет оборванные запросы сам — для заказа это
  выключено (`retries=0`). Оборванный ответ не означает «не дошло», он означает
  «неизвестно», и второй такой запрос был бы вторым заказом. На такой случай
  есть отдельное `OrderUnknown`: оно говорит посмотреть список заказов, а
  вкладка перечитывает его сама, не дожидаясь просьбы.

**Токен меняет цену ошибки в диагностике.** Без него СУЗ проверяет учётные
данные раньше маршрутизации: несуществующий `/order/nonsense` отвечает тем же
1110, что и настоящий метод, — выяснить, существует ли путь, невозможно. С
действующим токеном запрос доходит до маршрутизации, и коды ответов наконец
различают: 200 — метод есть и работает, 405 — такого пути нет, 400 с разбором —
путь есть, а данные не те.

Так и нашёлся настоящий путь. Прогон:

```
двойной клик по «Проверка СУЗ.bat»          (или tools\suz_probe.py вручную)
```

Сценарий берёт сохранённые реквизиты, обходит пути-кандидаты **только чтением**
и печатает, кто чем ответил, в файл «Ответ СУЗ.txt» рядом с программой.
Получения кодов (`/codes`) в нём нет и не будет: коды выдаются из буфера
безвозвратно, и «просто посмотреть» на них нельзя. Ни одного POST. Токен нигде
не печатается — файл можно отдать целиком.

Что он показал:

| Путь | Ответ |
|---|---|
| `GET /order/list` | **200** — вот он, список заказов |
| `GET /order/status` | 400 «Идентификатор заказа не найден» — путь есть, нужен номер |
| `GET /orders`, `/orders/list`, `/order`, `/orders/status`, `/buffer/status` | 405 — таких путей нет |

Единственного числа с `/list` было не угадать — угадать вообще ничего было
нельзя, и в этом весь смысл прогона.

Отсюда две особенности разбора:

- **Имена полей ищутся списком.** `orderInfos` или `orders`, `leftInBuffer` или
  `left` — читается любое из знакомых.
- **Незнакомый ответ не выдаётся за пустой.** Если списка заказов в ответе не
  нашлось вовсе, вкладка не показывает «заказов нет», а говорит прямо и
  записывает ответ целиком в `%APPDATA%\RetailCore\marking.log` — по записи
  разбор и правится. Пустой список при этом остаётся законным ответом «заказов
  не заводили».

Состояние заказа переводится только там, где мы в нём уверены; незнакомое
показывается дословно и помечается цветом. Выдать неизвестное состояние за
«Готов» — значит пообещать коды, которых нет.

По той же причине отдельно считаются «Получено» и «Кодов доступно»: первое —
`totalPassed`, второе — `leftInBuffer`, и они не связаны. А просроченный буфер
(`expiredDate` в прошлом) с ненулевым остатком помечается красным: коды в нём
ещё числятся, но забрать их уже нельзя, и показать их числом без оговорки
означало бы обмануть.

### Что проверено обращением к живой системе

Описания в открытых источниках расходятся между собой и с действительностью,
поэтому всё ниже установлено опытом, а не взято из статей.

| | Как есть на самом деле |
|---|---|
| Систем три | ГИС МТ `ismp.crpt.ru/api/v3`, True API `markirovka.crpt.ru/api/v3/true-api` и СУЗ `suzgrid.crpt.ru/api/v3` |
| Песочница | `markirovka.sandbox.crptech.ru` для первых двух, `suz.sandbox.crptech.ru` для СУЗ |
| Токен СУЗ | Заголовком `clientToken`, а не `Authorization: Bearer` |
| Вход в СУЗ | Свой, по УКЭП: `/auth/key` → подпись → `/auth/simpleSignIn`. Токен из чужой программы не нужен |
| Идентификатор соединения | В запросах **не участвует**: ни `ping`, ни вход его не спрашивают |
| Порядок проверок в СУЗ | Учётные данные — **раньше маршрутизации**: без токена все пути отвечают 1110 одинаково |
| Список заказов | `GET /order/list?omsId=`. Похожие `/orders` и `/orders/list` отвечают 405 |
| Буфер заказа | `leftInBuffer` и `availableCodes` — **разные** числа, плюс `totalPassed` и срок `expiredDate` |
| Создание заказа | `POST /order?omsId=`; в ответе `orderId` и `expectedCompleteTimestamp` |
| Подпись заказа | **Открепленная**, заголовком `X-Signature`. Наоборот, чем при входе |
| Количество на товар | От 1 до 2 000 000 — сказала сама СУЗ. 150 000 у ПРИНТМАРКИ — её собственный предел |
| Ошибки по полям | Лежат в `fieldErrors` (`fieldError`, `fieldName`), а не в `globalErrors` |
| Шаблон КМ | Свой у каждой товарной группы: духи 9, лёгкая промышленность 10, обувь 1, молоко 20 |
| Срок токена СУЗ | **10 часов**, из инструкции ЦРПТ. В ответе на вход не приходит — считается от выдачи |
| Идентификатор соединения | Нужен при запросе токена (`omsConnection`), в рабочие методы не уходит |
| Отказ СУЗ | **400, а не 401**: «Проверка учетных данных УОТ не пройдена», код 1110 |
| Текст ошибки СУЗ | Списком под `globalErrors`, а не строкой — разбирается отдельно от ошибок ГИС МТ |
| Кириллица в токене | Роняет запрос до отправки: заголовки уходят latin-1. Перехвачено и объяснено |
| `/api/v4` | Отвечает 403 на обоих хостах — True API живёт под третьей версией |
| Подпись | **Присоединённая** CAdES-BES. Отсоединённая отвергается: «Подпись невалидна. Код ошибки: 2» |
| Вход | `GET /auth/key` → подпись → `POST /auth/simpleSignIn` |
| Организация | ИНН **обязателен**, если сертификат по МЧД действует за нескольких |
| Список организаций | Отдаёт ГИС МТ через `/auth/cert/`, True API без ИНН только отказывает |
| Срок токена | В ответе не приходит; в описаниях расходится (10 часов против 10 минут) |
| Сведения о кодах | `POST /cises/info`, тело — **голый массив строк**, не объект |
| Что именно спрашивать | **Код идентификации** (`01`+GTIN+`21`+серийный). Тот же код вместе с криптохвостом (`91`, `92`) отвечает ошибкой |
| Разделитель GS | Сканер его часто **не выдаёт вовсе**. Конец серийного номера тогда ищется по началу криптохвоста — иначе номер «съедает» ключ и подпись |
| Размер пачки | **1000 кодов**; на 5000 сервер отвечает отказом с точным числом |
| Темп | 50 запросов в секунду от одного участника |
| Ненайденный код | Делает ответ целиком **404**, но с полным телом — это результат, а не ошибка |

Поэтому срок жизни токена нигде не зашит: он обновляется и по собственному
запасу, и прозрачным повтором входа на 401 — расхождение в описаниях перестаёт
что-либо значить.

### Устройство

Операция — запись в базе `%APPDATA%\RetailCore\marking.db`, а не вызов функции:
ГИС МТ отвечает «принято», а результат выясняется опросом, и операция обязана
пережить перезапуск. Пока ответа нет, повторная отправка запрещена — это был бы
второй вывод товара из оборота. Отправленную операцию нельзя даже удалить: запись
единственное свидетельство, что документ существует.

База локальной и останется: операция подписывается личным сертификатом
конкретного человека, а обмен идёт через саму ГИС МТ, а не через наш сервер.

### Чего ещё нет

Опрос статуса документов выключен признаком `STATUS_POLLING_READY` — метод и
состав ответа различаются по товарным группам, и догадка здесь однажды объявила
бы выполненной отклонённую операцию. Приёмка, отгрузка, вывод из оборота и
перемаркировка ждут описания API для парфюмерии и косметики из личного кабинета.

**Получение самих кодов** из буфера (`/codes`, `/order/codes/blocks`) и **отчёт о
нанесении** (`/utilisation`). Заказ заводится, буфер наполняется, а забрать коды
и отчитаться о нанесении пока нельзя. Получение кодов безвозвратно: выданный
блок повторно не выдаётся, поэтому делаться оно будет с сохранением полученного
на диск до отправки подтверждения, а не «сначала показать, потом думать».

**Ввод в оборот по кассовому чеку** (`/receipts/receipt`) — третий из нужных
сценариев. В СУЗ он отдельным разделом, а не частью заказа, поэтому и делаться
может независимо от него.

**Производство и импорт** как способы выпуска: им нужны `factoryId`,
`factoryCountry`, `productionLineId`, `productCode`, `productDescription` и
`expectedStartDate`. Отдел заказывает остатки и перемаркировку, поэтому они
сделаны первыми, а эти помечены неготовыми — вместо того чтобы отправлять заказ,
который ЦРПТ отклонит.

Какие методы у СУЗ вообще есть — выяснено по строкам библиотеки ПРИНТМАРКИ,
которой пользуется отдел, и совпадает с тем, что отвечает живая система:

| Метод | Для чего |
|---|---|
| `POST /order` | создать заказ |
| `GET /order/list`, `/order/status` | что заказано и в каком оно состоянии |
| `POST /order/close` | закрыть заказ |
| `GET /codes`, `/order/codes/blocks`, `/order/codes/retry` | получить коды блоками |
| `POST /utilisation` | отчёт о нанесении |
| `POST /aggregation`, `/dropout`, `/mod` | агрегация, выбытие, изменение |
| `GET /receipts/receipt`, `/receipts/document` | **ввод в оборот по кассовому чеку** |
| `GET /providers`, `/report/info` | справочники и отчёты |

Предпоследняя строка — ровно один из нужных сценариев, и он в СУЗ отдельным
разделом, а не частью заказа.

Поэтому на вкладке из операций есть только проверка: она ничего не меняет в ГИС
МТ. Кнопки «Принять» и «Вывести из оборота» появятся вместе с отправкой, а не
раньше — кнопка, которой нечего сделать, хуже её отсутствия.

## Отчётность для поставщиков

Вкладка `Отчётность` (`Ctrl+6`) собирает ежемесячный отчёт по акциям. Раньше это
делалось руками: выгрузка 1С → сводная таблица → удалить лишнее → сохранить под
именем месяца. Отчёт получался разным от месяца к месяцу — разъезжались колонки,
оставались технические поля, не было ни шапки, ни подписей.

### Как это работает

1. **Исходники.** Один файл со сводной по всем магазинам или несколько точечных
   выгрузок от разных менеджеров — они складываются в один отчёт. Шапка в
   выгрузке 1С ищется сама: блок «Параметры:» и «Отбор:» сверху и строка «Итого»
   снизу в отчёт не попадают.
2. **Магазин.** Берётся из колонки файла. Если её нет — из имени файла
   («Продажи Уссурийск июнь 2026.xlsx» → «Уссурийск»); кнопкой «Задать магазин»
   его можно поправить.
3. **Объединение магазинов.** Продажи магазина-источника учитываются за
   магазином-приёмником по общим правилам (см. ниже).
4. **Сводная.** Строки, колонки, показатели и отбор берутся из профиля отчёта.
5. **Файл.** Имя по шаблону («Июнь 2026»), период — из самих данных, а не из
   даты выгрузки.

### Профиль отчёта

Формат отчёта для одного поставщика: какие поля идут в строки, какие в колонки,
какие показатели считаются и что отсекается фильтром. Значения по умолчанию
повторяют отчёт, который собирался руками: строки — номенклатура, колонки —
акция, показатели — количество и сумма автоматической скидки, отбор — только
акционные продажи.

Показатели: количество, сумма авт., скидка бонусами, скидка всего, сумма продаж,
начислено бонусов. «Скидка всего» — не колонка выгрузки, а сумма автоматической
и бонусной: разделять их или складывать, решает профиль.

В шаблонах имени файла и заголовка подставляются `{Месяц}`, `{Год}`,
`{Поставщик}`.

### Объединение магазинов

Правило «магазин-источник → магазин-приёмник» переносит продажи одной точки на
другую. Правила **общие для всех менеджеров**: если один учитывает
интернет-магазин за универмагом, а второй нет, сводная по сети перестаёт
сходиться, а найти причину по готовым файлам уже нельзя.

Применяются по цепочке: `A → B` и `B → C` довезут продажи `A` до `C` за один
проход. Названия сравниваются нестрого — регистр, двойные пробелы и «ё» в
выгрузках гуляют, — но по совпадению целиком: «Артем (Первый Парфюмерный)» не
объединится с «Первым Парфюмерным».

Источник уникален: отправить один магазин сразу в два — это молча удвоенные
продажи. Кольцо (`A → B → A`) не даст себя создать, а если оно уже в базе —
переносы не применяются вовсе и вкладка об этом предупреждает: половина
переноса хуже, чем ни одного.

### Что в готовом файле

Шапка с поставщиком, периодом и списком магазинов; двухэтажная шапка таблицы с
объединением по разрезу; числовые форматы (`#,##0` и `#,##0.00` — вместо
`3160.1000000000004` в ячейке); ширины колонок по содержимому с потолком;
закрепление области и автофильтр по данным без строки «Итого»; выделенная строка
итога; подписи из профиля; печать в альбомной ориентации со сквозной шапкой.
По желанию — отдельный лист «По магазинам» с итогами по каждой точке.

### Где лежит

**Общая база** — на сервере: профили отчётов и правила объединения магазинов
видит и правит любой пользователь. Удалять профиль или правило может только
администратор — на них опираются чужие отчёты.

**Локальная база** — `%APPDATA%\RetailCore\reports.db`. Используется, если вход
в общую базу не выполнен.

### Ведомость по складам

Вторая вкладка раздела, к отчёту поставщику отношения не имеющая: она разбирает
выгрузку **«Ведомость по товарам на складах»** из 1С. Читать её глазами нельзя —
на каждый склад по четыре колонки, складов бывает шестнадцать, строки групп идут
вперемешку с товарами, а итог стоит рядом с данными.

Выбираете файл, нажимаете «Разобрать» — получаете пять срезов:

| Срез | О чём |
|---|---|
| **Не хватило** | Расход был, а на конец периода не осталось ничего |
| **Топ товаров** | По расходу, с долей и числом магазинов, где он расходился |
| **По магазинам** | Магазины по расходу, под каждым — что расходилось лучше |
| **Свод** | Товары в строках, магазины в колонках: расход и остаток рядом |
| **Ошибки учёта** | Отрицательные остатки |

То же самое сохраняется в Excel — по листу на срез, выводы первым листом.

**Чего вкладка намеренно не говорит.** Слово «продажи» не используется: в расход
попадают ещё списания и перемещения между складами, а разделить их в этой
выгрузке нечем — колонка одна. Расчётов «на сколько дней хватит» тоже нет:
период выгрузки в файле не указан. И «кончилось» — это факт, а не потерянные
продажи: дат в выгрузке нет, товар мог кончиться в последний день периода.

**Какой вид отчёта подходит.** Отчёт в 1С у каждого подразделения настроен
по-своему, и вкладка узнаёт несколько видов:

| Вид | Как выглядит |
|---|---|
| **Склады в колонках** | На каждый склад блок «Начальный остаток · Приход · Расход · Конечный остаток»; блок «Сумма» рядом с «Количеством» пропускается |
| **Склад колонкой** | Плоская таблица, склад указан в каждой строке |
| **Склады группами строк** | Строка склада, под ней группы и товары. Нужна группировка строк Excel — без неё склад не отличить от группы товаров |
| **Один склад** | Складов в шапке нет; название берётся из отбора «Склад Равно …», иначе из имени файла |

Подписи узнаются в разных написаниях: «Номенклатура», «Номенклатура,
Характеристика», «Товар»; «Начальный остаток» и «Остаток на начало»;
«Приход» и «Поступление». Обязательны «Расход» и «Конечный остаток». Без
начального остатка или прихода разбор идёт, но доля «ушло от запаса» не
показывается — запас неизвестен, и ноль на его месте был бы выдумкой.

Если файл не узнан, сообщение говорит, что в шапке нашлось и чего не хватило:
по нему видно, какое поле добавить в настройках отчёта в 1С.

**Несколько файлов.** Можно выбрать сразу несколько — например, по файлу от
каждого магазина, — и они сведутся в одну ведомость, даже если вид у них
разный. Товары сводятся по коду 1С, без него — по артикулу, названию и единице.
Одноимённые склады из разных файлов не складываются, а разводятся номером:
скорее всего, это один файл, выбранный дважды. Если итог не сошёлся в одном
из файлов, предупреждение называет этот файл.

**Что вкладка ловит сама.** Шапка читается по подписям, а не по номерам колонок,
поэтому состав складов может меняться. Склады с одинаковым названием разводятся
номером — «Пирожок (2)», — потому что группировка по имени теряет данные одного
из них. Строки групп не считаются: их числа — итоги вложенных товаров. Склады
«в пути» в расход не идут, но их остаток показан отдельно, иначе товар в пути
выглядит пропавшим.

Колонка «Итого» из отчёта — или строка «Итого» внизу, если колонки нет, —
обращена в проверку: сумма по складам сверяется с ней, и при расхождении
вкладка говорит, что числам верить нельзя. Отчёт с неверно
прочитанной шапкой выглядит целым — числа просто встают не под тем складом.

Отрицательный остаток вынесен отдельно от нехватки: расход больше, чем было на
складе, — это непроведённый приход или пересорт, и завозом он не лечится.

## История данных

Каждая загрузка каталога сохраняется целиком в локальную базу
`%APPDATA%\RetailCore\snapshots.db`, поэтому состояние ассортимента и цен
на любую прошлую дату остаётся доступным: можно сравнить прайс за август с
прайсом за сентябрь, увидеть, какие позиции появились и на сколько выросли
цены. Снимок делается сам, в фоне, ничего нажимать не нужно.

Снимаются только каталоги — на страницах «Сопоставление» (основной и
дополнительные прайсы) и «Каталог». Целевой файл и бланк заказа не снимаются:
это то, что заполняется, а не источник данных.

Повторная загрузка того же файла новую версию не создаёт — версии различаются
по содержимому (SHA256), а не по имени или времени. Изменился файл — появился
новый снимок.

На вкладке **«История данных»** (`Ctrl+4`):

| Действие | Что делает |
|---|---|
| Открыть | Состояние каталога на выбранную дату, с поиском |
| Сравнить версии | Новые и удалённые позиции, изменение цен и характеристик |
| Удалить | Убирает снимок после подтверждения и освобождает место на диске |

Каталог на 100 000 товаров занимает около 28 МБ и записывается примерно за
секунду. Автоматической чистки нет: история нужна за годы, поэтому снимки
удаляются только вручную. Отключить сохранение можно в «Настройках» →
«История данных», там же показан текущий размер базы.

Ход импорта пишется в `%APPDATA%\RetailCore\snapshot.log`.

## Обновления

Приложение само проверяет новую версию на GitHub Releases при каждом запуске
и предлагает обновиться — категорийным менеджерам не нужно ничего скачивать
вручную. Настройки поведения — на странице «Настройки» → «Обновления»
(проверять автоматически, загружать автоматически, показывать список
изменений); журнал — `%APPDATA%\RetailCore\update.log`.

Релизы берутся из [QBEEL/RetailCore-Perviy](https://github.com/QBEEL/RetailCore-Perviy)
— репозиторий задан в [app/ui/update_check.py](app/ui/update_check.py) и должен
оставаться публичным: проверка идёт без токена, а приватный репозиторий
потребовал бы встраивать токен в exe, раздаваемый пользователям, откуда его
несложно извлечь.

**Публикация новой версии:**

1. В [app/__init__.py](app/__init__.py) поднимите `__version__` (semver:
   `MAJOR.MINOR.PATCH`).
2. Соберите exe: `.venv\Scripts\pyinstaller.exe RetailCore.spec --noconfirm --clean`.
3. Посчитайте контрольную сумму:
   ```
   certutil -hashfile "dist\RetailCore.exe" SHA256
   ```
4. Создайте `version.json` (не путать с `__version__` в коде — это отдельный
   файл, который публикуется только на GitHub, в репозитории его нет):
   ```json
   {
     "mandatory": false,
     "sha256": "<хеш из шага 3>",
     "changelog": ["Что изменилось", "Ещё один пункт"]
   }
   ```
   `mandatory: true` не даёт пропустить версию или отложить обновление —
   используйте только для критичных исправлений.
5. На GitHub: **Releases → Draft a new release**, тег `vX.Y.Z` (например,
   `v2.4.0`, обязательно с `v`), к релизу приложите два файла:
   `RetailCore.exe` и `version.json`. Заголовок и описание релиза —
   произвольные, приложение их не читает (текст «Что нового» берётся из
   `changelog` в `version.json`).
6. Опубликуйте релиз. Проверьте на тестовой машине со старой версией: при
   запуске должно появиться уведомление о версии `X.Y.Z`.

## Настройки

Хранятся в `%APPDATA%\RetailCore\settings.json`: выбранные поля поиска и
их веса, пороги, размеры окна, недавние файлы, ручные правки ролей колонок,
выбранные листы, исключения переноса, профили поставщиков и настройки
переоценки, настройки автообновления и истории данных. Сохраняются
автоматически.

Настройки переоценки открываются кнопкой «Настройки» на вкладке «Быстрая смена
цен»: по каким полям искать товар (артикул, внутренний код, штрихкод, название,
нечёткое сравнение), что игнорировать при сравнении кодов (регистр, пробелы,
специальные символы), минимальный процент совпадения, разделители артикула и
нужно ли исключать из файла товары без изменения цены.

Маркировка запоминает там же выбранный сертификат (отпечаток), контур, список
организаций, за которые действует сертификат, и ту из них, под которой
выполняется вход. Список хранится потому, что узнаётся он только обращением к
закрытому ключу, — иначе каждый вход требовал бы лишнего пароля к контейнеру;
при смене сертификата он забывается. Токена среди настроек нет: он живёт
полчаса и всё равно требует обращения к ключу. Неизвестное значение контура читается
как песочница — подставлять боевой по испорченному файлу настроек нельзя.

Реквизиты СУЗ лежат не здесь, а в отдельном `marking_suz.json` с ограниченными
правами: в нём токен устройства, а `settings.json` копируют и пересылают.

В той же папке лежат история данных (`snapshots.db`), база поставщиков
(`suppliers.db`), операции маркировки (`marking.db`) и журналы `update.log`,
`snapshot.log` и `price.log`. Открыть её можно кнопкой в «Настройках» →
«История данных».

Профили поставщиков раньше хранились в `settings.json`; при первом запуске
версии с базой они переезжают в `suppliers.db` сами. Поле в настройках
остаётся, чтобы старая версия приложения продолжала работать с тем же файлом.
