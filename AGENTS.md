# RetailCore: инструкции для Gemini и других агентов

## Роль и работа с пользователем

Ты помогаешь разрабатывать RetailCore совместно с пользователем и Codex.
Общайся по-русски, объясняй выводы конкретно и кратко.
Явные указания пользователя определяют задачу и имеют приоритет над этим файлом.

Если задача не уточнена, начни с независимого ревью: изучи код, найди проблемы
и предложи исправления. В режиме ревью не меняй файлы. Если пользователь поручил
реализацию, выполни её и необходимые проверки; не ограничивайся планом.

Не утверждай, что связался с Codex или получил его ответ, если реального канала
связи нет. Передавай результаты через пользователя или согласованный файл отчёта.

## Первое знакомство

1. Прочитай этот файл, `README.md` и `DEPENDENCIES.md`.
2. Проверь `git status --short`, текущую ветку и последние коммиты.
3. Прочитай файлы, относящиеся к задаче, и их тесты.
4. Для серверных задач дополнительно прочитай `server/DEPLOYMENT.md`.
5. Для сборки и выпуска изучи `.github/workflows/tests.yml` и `build.yml`.

Не считай сведения из старого отчёта актуальными без проверки кода.
Версию приложения бери из `app/__init__.py`.

## Устройство проекта

- `run.py` — запуск настольного приложения.
- `app/ui/` — интерфейс PySide6, страницы и главное окно.
- `app/ui/widgets/` — переиспользуемые элементы интерфейса и диалоги.
- `app/core/` — обработка данных и прикладная логика.
- `app/core/marking/` — интеграция с «Честным знаком», авторизация,
  документы, статусы и локальный журнал.
- Остальные модули `app/core/` отвечают за оплаты, поставщиков, заказы,
  переоценку, отчёты, претензии, почту, заметки, историю данных и VPN.
- `server/api/` — серверное API на FastAPI; PostgreSQL хранит общие данные.
- `server/api/app/migrations.py` — применение и проверка SQL-миграций.
- `server/db/` — SQL-схема и миграции; `server/tools/` — обслуживание сервера.
- `tests/` — тесты клиента и сервера.
- `tools/` — утилиты сборки и выпуска.
- `RetailCore.spec`, `RetailCore.macos.spec` — сборки PyInstaller.
- `legacy/` — исторический код; проверяй актуальную реализацию в `app/`.

Клиент выпускается для Windows и macOS. CI и сервер используют Python 3.12.
Зависимости закреплены точными версиями и SHA-256.

## Совместная работа и Git

- Перед правками согласуй область работы с текущей задачей: какие файлы меняешь
  ты, какие — другой агент. Для параллельной реализации используй отдельную
  ветку и рабочую копию либо Git worktree.
- Не перезаписывай чужие изменения. Если файл изменился во время работы,
  перечитай его и учитывай актуальную версию.
- Не используй `git reset --hard`, `git clean`, force push и перенос тегов
  для устранения обычных конфликтов.
- Добавляй в коммит конкретные файлы. Не применяй `git add .` без проверки:
  в рабочей папке могут находиться реальные УПД, изображения и другие
  пользовательские данные, которые не предназначены для репозитория.
- Коммиты, push, теги и публикацию выполняй в рамках поручения пользователя.
  Уже данное разрешение не запрашивай повторно.
- Не меняй номер версии и не создавай релиз для обычного ревью.

## Правила реализации

- Сохраняй текущий стиль и существующие интерфейсы, предпочитай небольшие
  изменения с понятной причиной. Не добавляй рефакторинг, не связанный с задачей.
- Длительные сетевые операции и обработку больших файлов выполняй вне
  потока интерфейса; обновляй Qt-виджеты в потоке GUI.
- Сохраняй совместимость пользовательских настроек и локальных данных.
- Не редактируй уже применённые SQL-миграции: их контрольные суммы проверяются.
  Изменение схемы оформляй новой миграцией по существующим соглашениям.
- Ограничения зависимостей меняй в `.in`, затем пересоздавай соответствующие
  `.txt` по `DEPENDENCIES.md`. Не отключай проверку хешей для обхода ошибки.
- Токены, пароли, подписи, сертификаты, рабочие базы и реальные документы
  не помещай в код, логи, отчёты и коммиты. Для примеров используй синтетические данные.

## Особое внимание: «Честный знак»

- Авторизация True API переведена на UUID-токены. Изучи
  `app/core/marking/session.py` и `tests/test_marking_uuid_auth.py`.
  Не возвращай зависимость от декодирования JWT.
- При изменении протокола сверяйся с актуальной официальной документацией ЧЗ.
- Сопоставляй статус строго с идентификатором запрошенного документа.
  Первый элемент списка не является подходящей заменой.
- Ошибка сети, незнакомый статус и отсутствие документа в ответе
  не означают успешное завершение операции.
- Обновление статуса не должно повторно отправлять документ. Учитывай
  контур, товарную группу и защиту от конкурентного изменения записи.
- Реальную отправку, подписание и другие действия с рабочими документами
  выполняй только в рамках явно порученной пользователем операции.
- Отличай тесты с подменой сети от проверки реального входа с электронной
  подписью. Не объявляй реальный вход проверенным по результатам unit-тестов.

## Проверки

Из корня проекта, в выбранном виртуальном окружении, PowerShell:

```powershell
python -m pip install --require-hashes --only-binary=:all: -r requirements-test.txt
$env:QT_QPA_PLATFORM = 'offscreen'
$env:PYTHONUTF8 = '1'
python -m pytest tests -q -ra
```

Для небольшой правки сначала запускай относящиеся к ней тесты.
Для изменений бизнес-логики, хранения данных и интеграций добавляй проверки
существенных сценариев и ошибок. Перед выпуском обязателен полный CI.

Тесты не должны обращаться к рабочей сети, электронной подписи, реальному
хранилищу паролей или пользовательским базам. В тестовых главных окнах
отключай `update_check_auto`, если не проверяется само обновление:
отложенные сетевые запросы могут вмешаться в последующие тесты.
Windows-зависимые проверки реестра и DPAPI ограничивай платформой.

Тесты миграций требуют `RETAILCORE_TEST_DSN`, указывающий на отдельный тестовый
PostgreSQL. Они создают и удаляют тестовые базы. Рабочий DSN использовать нельзя.
Без DSN часть проверок пропускается — указывай это в отчёте.
Серверный CI отдельно проверяет миграции и запуск Docker Compose с чистой базой.

## Сборка и выпуск

```powershell
python -m pip install --require-hashes --only-binary=:all: -r requirements-build.txt
python tools/fetch_singbox.py
python -m PyInstaller RetailCore.spec --noconfirm --clean
```

Результат Windows — `dist/RetailCore.exe`; macOS собирается своим spec-файлом
на macOS. Самопроверка Windows выполняется на синтетических книгах:

```powershell
& .\dist\RetailCore.exe --selftest каталог.xlsx цель.xlsx отчёт.txt
```

При порученном выпуске версия в коде должна совпадать с тегом `vX.Y.Z`.
Добавь раздел в `CHANGELOG.md` с понятными пользователям изменениями.
Дождись успешного CI и проверь опубликованные `RetailCore.exe`,
`RetailCore.dmg` и `version.json` с обеими контрольными суммами.
Репозиторий исходников — `QBEEL/RetailCore-Perviy`, публичных обновлений —
`QBEEL/RetailCore-Releases`. Не считай push тега завершённой публикацией.

После подтверждённой публикации релиза проверь, изменились ли файлы `server/`
относительно работающей на сервере версии. Если изменились, в рамках порученного
выпуска обнови рабочий сервер по `server/DEPLOYMENT.md`: проверь состояние,
сохрани резервную копию, выполни обновление и проверь версию API и доступность.
Не объявляй выпуск завершённым, пока серверная часть не обновлена или не названа
конкретная причина, по которой обновление не удалось.

Описание нового выпуска должно попадать в окно «Обновления»: проверяй раздел
`CHANGELOG.md`, опубликованный `version.json` и отображение списка изменений
в диалоге. После выпуска покажи пользователю в отчёте, что нового в программе.

## Формат результата

В ревью сначала перечисли подтверждённые проблемы по важности. Для каждой:
файл и строка, сценарий воспроизведения, последствия, предлагаемое исправление.
Отделяй доказанные ошибки от предположений. Если проблем не нашёл, скажи об этом.

После реализации сообщи: что изменено, какие проверки прошли,
что осталось непроверенным. Не выдавай планируемые действия за выполненные.
